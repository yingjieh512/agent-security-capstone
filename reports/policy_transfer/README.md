# 留出策略能否只靠声明和来源能力接入？

## 独立策略和判定

已接受的邮件必须有批准，且 SMTP 信封收件人与批准相同。**发出完整的一组获批文件内容时，允许改名。只发其中一部分时，内容和文件名都必须分别落在批准的清单与份数内。** 文件名与内容分别计数，部分发送时可以使用来自另一份获批附件的合法名称。正文可以修改。上轮只看收件人和附件内容的验证器，会放过部分发送时的未授权改名或重复使用名称。[作者声明及案例](independent_proxy/cases.json)

授权快照先提交到独立审批表并签发回执，再向仅监听本机的 Mailpit v1.34.0 发邮件。投递端按 SMTP 队列 ID 从 REST 读取实际信封收件人与解码附件。计分器按 Message-ID 从已落库的原始 MIME 另行解析，由全文授权规则计算真值。两条路径共享邮箱、服务端的信封来源和审批表。作者封存的 16 个标签全部与独立 MIME 判定一致。试验没有使用真实邮箱地址或真实邮件正文。

- **作者组。** 16 个手写场景各配四个正文长度模板，64 次 SMTP 投递，28 次合法、36 次越权。四个模板来自固定的 ATBench send_email 和 Claw gog gmail send 调用，仅借用了原正文长度。
- **预设组合组。** 在收到题目前生成的 32 个收件人、正文、附件数量、文件名与内容变异组合，每个执行一次。6 次合法、26 次越权。含最多四份附件，超过编译时每端最多两份的搜索范围。此组的内容替换同时改变文件大小。
- **计分口径。** 正确确定数以全部已接收邮件为分母。64 次作者组投递是同 16 个案例的重复实例。96 次是受控集功能覆盖，不能用于估计自然邮件的越权发生率。

## 系统给出的三项可复验证据

1. **缺记的字段能定位到来源。** 缺字段配置只留整组文件的内容标签。搜索器举出的例子是，同一收件人获批两份名为 `a.bin`、内容为 A 的文件。实际只发一份时，发 A 合法，发等长的 B 越权。两次收件人相同、文件名相同、整组内容标签都与批准不等。另用两封 SMTP 邮件复现了相同观察和相反真值。建议在审批与投递两端各补一项逐文件内容标签。应用后，24 次未知全部得到正确判定。只补字段会保留原有整组标签，故记录比从头生成的配置大。[反例与最小增加项](results.json)
2. **不必要的敏感字段能删。** 在手写过量配置自己的 14 个源端字段内搜索，留下两端各三项：收件人标签、逐文件内容标签、文件名清单。删掉两端的明文收件人、正文、可恢复附件内容及大小列表，日志总大小由 222,492 降到 139,336 字节，减少 37.4%。明文收件人由 3,384 字节减为 0，正文由 58,824 减为 0，可恢复附件内容由 752 减为 0。文件名仍有 3,196 字节，标签仍披露同次操作的相等关系和重复次数。这些是双端审计回执的留存量，邮箱仍须短暂保存合成邮件。大小收益取决于这些模板和编码。
3. **有些敏感字段在新策略下必须保留。** 上轮策略可以删文件名。这次的菜单中，只有明文文件名可用于逐名称比较。主实验后做了一次能力限制检查，分别从审批端或投递端拿掉文件名能力，其余字段全部可用。两次搜索都拒绝生成完整配置并给出反例。比如批准两份 `a.bin`，同样只发出一份内容 A，命名 `a.bin` 合法，命名 `b.bin` 越权。投递端若不记录名称，即使拥有两端全部附件原文也无法区分。两对反例又通过 4 次 SMTP 接收核实。这是现有投影菜单的限制，将来若提供逐文件名的按操作比较标签，可能无需保留原文。[能力限制结果与邮箱复验](filename_capability_check.json)

编译时两个来源各有 10 种候选字段，一共有 1,048,576 个可选组合。冻结的搜索器按可恢复原文字段数、源端字段数、披露排序依次择优。此次从候选队列取出 114 个配置，对其中 11 个做完整性审计，利用相反标签的同观测反例跳过其他组合。选出的配置在 12,544 个双端均有记录的有限世界中通过运行时核验。这个结论限定于字段目录、选择成本、可见信息和冻结解码器。认证信封中的操作号、角色、正负状态、策略摘要和 MAC 也会占用字节。[实现](../../scripts/mail_policy_search.py) · [签发和验证](../../scripts/mail_policy_runtime.py)

## 项目判断和复现

本次验证支持将“根据审计策略和来源能力生成可执行日志，给出遗漏证据的实例，并随策略改变隐私留存”作为学期项目的核心。系统在同一后端对文件名给出了两种不同结论，且在新规则披露后无需再改核心代码。当前仅有一条独立代理命题的留出策略，强手写与自动打平。真实开发者的耗时、出错率和语言之外的策略仍需单独验证。真人出题者可独立使用同一份说明，并把三个 JSON 交给相同入口。

使用 Python 3.10+、前轮同一数据副本与仓库依赖。先按[上轮报告](../attachment_holdout/README.md)安装本地 Mailpit。下例在仓库根目录运行。主实验在本机一次耗时约 2.6 秒，不需要 GPU 或模型推理。重跑后的聚合 JSON 与本次留档逐字节一致。

```bash
STUDY=reports/policy_transfer
PYTHONPATH=src python scripts/compile_mail_policy.py --policy "$STUDY/independent_proxy/policy.json" --capabilities "$STUDY/capabilities.json"
PYTHONPATH=src python scripts/run_declaration_holdout.py --bundle "$STUDY/independent_proxy" --out outputs/policy_transfer/recheck.json
cmp "$STUDY/results.json" outputs/policy_transfer/recheck.json
PYTHONPATH=src python scripts/check_mail_policy_omission.py --policy "$STUDY/independent_proxy/policy.json" --capabilities "$STUDY/capabilities.json" --field attachment_names.raw --out outputs/policy_transfer/check-filename.json
RUN_LOCAL_MAILPIT=1 PYTHONPATH=src python -m pytest
```
