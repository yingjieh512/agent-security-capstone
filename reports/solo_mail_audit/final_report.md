# 邮件代理的授权规则变了，下一封该记什么？
**Yingjie Huang　｜　单人 Capstone 项目报告　｜　2026 年 11 月**

审批系统允许发出两份附件 A、B，邮箱实际只收到 A。按“整组必须相同”，这封邮件越权。改成“可以少发”后，同样的发送获批。只留下两组附件的摘要，审计者知道两组不同，却分不清是少发了获批文件，还是多发了未获批文件。这个项目把“日志还够不够用”做成了可以在部署前回答的问题。

## 已实现的系统
操作者提供新授权规则、审批端与投递端能记录的字段，以及当前采集配置。系统搜索能判定规则的双端字段，逐端列出需要增加和停止记录的项。若旧配置会混淆合法与越权，它给出一对可送到本地邮箱的反例。若可用字段都无法区分两种结论，系统拒绝激活该规则。

| 阶段 | 产物与作用 |
| --- | --- |
| 编译与解释 | 在给定字段菜单和披露成本顺序中搜索。可选表示包括原文、一次发送内可比较的标签、附件清单或数量。 |
| 版本化部署 | 可行配置写入 SQLite。创建发送尝试时固定策略版本，分别在审批和投递时生成带认证码的回执。 |
| 离线审计 | 验证两端回执，用当时的策略判为获批、越权或证据不足。操作者可以关掉邮箱后重新核验。 |

## 项目的贡献
从安全策略推导日志需求、为程序合成数据最小化器、在代理执行动作时按字段控制披露，均有已有工作。本项目把问题落到**策略迁移**上：审批和投递分别缺什么证据，反例能否由真实邮件后端重放，以及跨版本的在途发送最终依据哪条规则复核。这些问题分别有可执行工具、受控实验和切换演示支持。[目标驱动审计](https://seclab.cs.ucdavis.edu/papers/tocs-96.pdf) · [数据最小化器合成](https://arxiv.org/abs/1611.05642) · [代理动作字段分级](https://arxiv.org/abs/2608.25474)

56 次规则变更中，46 次能复现旧证据的歧义。按新规则生成的配置与统一固定配置都正确判定了 512/512 项，前者的认证回执总字节少 56.7%。下文给出分母、固定对照以及必须增加敏感留存的条件。

# 规则切换时，哪些证据必须增删？
## 实验怎样计分
每条规则都要求 SMTP 信封收件人与批准的一致，再加一个条件。八个条件是附件内容、名称或长度分别满足整组相等或按份数包含，以及正文相等、附件份数不超过批准数。八条规则两两切换，共 56 个有向变更。编译器、解释器、搜索器与回执验证逻辑冻结于提交 `f15e621`。搜索在 12,544 个双端有限状态组合中检查充分性。

16 种发送情形包括换收件人、改正文、附件重排、多发重复件和无批准等。每种配四个来自 ATBench 与 Claw 的正文长度，构成 64 次本地 SMTP 投递。授权、地址、正文及附件均为合成。取证端从 Mailpit 接口取实际投递事实。计分端另读落库 MIME，与发送前保存的完整审批快照比较。正确覆盖率以全部应判项为分母，包含未能判定的项。

| 同批投递 × 八条规则 | 固定通用配置 | 按规则编译 |
| --- | ---: | ---: |
| 正确判定 / 应判 | 512 / 512 | 512 / 512 |
| 误放、误报、证据不足 | 0、0、0 | 0、0、0 |
| 完整认证回执（字节） | 1,250,720 | 541,668 |
| 明文正文（字节） | 484,096 | 60,512 |
| 明文文件名（字节） | 12,256 | 3,064 |
| 明文地址、可还原附件内容（字节） | 0、0 | 0、0 |

固定配置由本项目预先指定，在两端记录收件人标签、逐附件内容标签、正文、文件名及长度，能覆盖八条规则。自动配置使明文正文减少 87.5%，文件名减少 75.0%。指标只计审计回执。承载原邮件的业务邮箱本身仍有正文和附件。

## 一对能实际发送的反例
从“整组相等”改到“允许部分发送”时，批准 A 却发空清单，与批准空清单却发 A，都会得到“两端整组标签不同”。前者获批，后者越权。系统输出这对发送，并把两端的整组标签改为逐附件标签。再切换到“只限制份数”时，改记数量即可，连附件间的内容相等关系都可以省去。

共有 46 次变更需要补证，每次都用两封邮件重放，92 次额外 SMTP 接收对应 8 对不同反例。另有 6 次可进一步减记，4 次可沿用旧字段。沿用旧配置时有 1,672/3,584 项正确、1,912 项证据不足。应用字段变更后，3,584/3,584 项正确。这些判定复用同一批 64 封邮件。

# 一个来源少给一个字段，系统会怎么做？
在最终实验前固定验收协议（提交 `100b63b`）。对八条规则，在审批端或投递端单独撤掉十种可用字段之一，得到 8 × 2 × 10 = 160 个设置。每次只撤一个字段，另一端保留完整菜单。另设八个完整菜单对照。把某端新启用的可还原原文单独计数，即使另一端原先已经在记录同类信息。

| 搜索结果 | 设置数 | 含义 |
| --- | ---: | --- |
| 沿用原配置 | 128 | 失去该字段后，原先选中的采集项仍然可用。 |
| 替代配置，无新增原文字段 | 4 | 例如用逐附件标签核验整组相等。 |
| 替代配置，新增原文字段 | 22 | 16 项新增收件人原文，6 项新增附件内容原文。 |
| 无充分配置，拒绝激活 | 6 | 每项均找到一对观察相同、授权结论相反的执行。 |

154 个可行设置复用 64 封本地邮件，共 9,856/9,856 项正确，误放、误报、未知均为 0。相同规则和字段配置复用同一份判分，实际测量了 24 种不同的规则与配置组合（含对照）。另 6 个不可行设置均完成反例重放，共 12 次额外 SMTP 接收，去重后是 4 对反例。八个完整菜单对照的覆盖与字节数复现了主实验。

## 更短的日志也能暴露更多个人信息
只撤掉一端的收件人比较标签，核验地址相等就需要两端都改记可还原的地址。在其中一条规则的 64 封邮件上，回执总量反而少了 **16,244 字节**，但新增 **2,232 字节**可还原地址。低存储开销可以伴随更高隐私代价。因此报告分别给出回执总字节与每种可还原内容的字节。

## 能力不足时为什么要拒绝
按文件名核验相等或包含时，只要有一端无法记录名称，剩余菜单就可能混淆同内容、同长度但名称不同的附件。按正文相等核验时，缺一端正文也有同样问题。前者覆盖四个设置，后者覆盖两个。这六个设置在部署前被拒绝，未计入成功覆盖或节省字节的分母。

“最小”由给定字段菜单、披露成本顺序和有限状态域共同限定。可比较标签仍可能泄露本次发送内的相等关系、文件数量和重复模式。22 个回退结果使操作者可以在部署前看到新增的敏感留存。

# 在途发送怎样审计，如何复现？
在同一个持久工作区中激活四个策略版本，经本地 SMTP 发出四封邮件。第一封在 v1 下审批，投递前切到 v2。第二封使用相同的批准内容与投递内容，但在 v2 下开始。两封邮件应得到不同结论。

| 本地发送 | 生效规则与两端保留的附件信息 | 回执判定 |
| --- | --- | --- |
| v1 审批后切到 v2，批准 A、B，发 A | v1 整组相等，整组标签 | 越权 |
| v2 新审批，同样批准 A、B，发 A | v2 允许部分发送，逐件标签 | 获批 |
| v3 按数量授权，发不同内容但份数合规 | v3 只限制份数，记录数量 | 获批 |
| v4 恢复到最初规则，再次少发 | v4 整组相等，整组标签 | 越权 |

四项均与落库 MIME 的参考结论一致，关闭邮箱后重新打开工作区仍可核验。尝试部署缺少文件名证据的规则时，激活失败，当前版本保持 v2。重复激活 v4 沿用同一版本。投递回执尚未到达或验证密钥错误时，结果为证据不足。

## 复现与课堂演示
在交付包根目录使用 Python 3.10+。第一条命令运行三个实验并与归档 JSON 逐项比对。首次使用会下载并校验 Mailpit v1.34.0，也可用本地官方压缩包离线安装。第二条命令读取一封可编辑的 JSON 案例，输出审批版本、实际采集字段、判定及落库参考值。

```sh
python3 scripts/reproduce_mail_capstone.py
PYTHONPATH=src:scripts python3 scripts/run_mail_case.py examples/mail_audit/local_case.json
```

课堂上先展示批准 A、B 却只发 A 的两个版本，再把规则切到只限制份数，看双端字段变成数量。最后用收件人标签缺失的结果说明为什么必须单列可还原地址。[版本演示结果](workspace_demo.json) · [策略迁移结果](results.json) · [来源能力结果](capability_results.json)

## 可以主张的研究结论
在单收件人、本地后端、八条受控规则内，系统能在启用新规则前定位缺证，在业务继续发送时保存当时的审计语义，并量化维持覆盖所需的敏感留存。上述结果支持一个可演示和可复现的单人系统贡献。ATBench 与 Claw 只提供四个正文长度。固定对照由作者预设，真人配置效果及生产流量上的改善仍待验证。审批端、投递端、密钥和本地版本库均被信任。两条判分路径共享邮箱与审批事实。系统核验已发生的发送，未评估实时拦截效果。
