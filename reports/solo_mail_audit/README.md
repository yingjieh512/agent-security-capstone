# 单人 Capstone：邮件代理授权策略变更后的最小审计日志

**研究问题。** 邮件代理的授权规则变了，已有日志还能证明下一封邮件有没有越权吗？如果不能，审批端和邮箱端分别需要多记什么？如果规则变简单，又有哪些敏感字段可以停止收集？

**可交付的系统。** 输入旧字段配置、新策略和两端可记录的字段，命令行工具输出新的收集配置、逐端增删清单，以及旧证据不足时的一对具体反例。审批端和投递端按目标配置为新的发送签发回执。审计者从回执得出“获批”“越权”或“证据不足”。整个实验由一人在一台电脑上执行，使用合成本地邮件和自动计分。实现、反例演示、固定对照、复现脚本和本次测量均已入库。[迁移工具](../../scripts/plan_mail_policy_change.py) · [单人实验入口](../../scripts/run_solo_mail_audit.py)

## 可以直接讲给老师的例子

最初的规则要求发送**完整且完全相同的一组附件**。审批端与投递端分别记录一个只对本次操作有效的整组内容标签，标签相同就能确认内容一致。后来规则改为**允许发送获批附件的一部分**。这时标签不同有两种解释。批准一份 A 实际发送空清单，是合法少发。批准空清单却实际发送一份 A，是越权多发。两次的收件人均正确，整组标签都不相等，旧配置给审计者的可比较信息相同。系统生成这对反例后，把两端的整组标签替换为逐附件比较标签。这样能比较具体内容及重复份数，又无需把附件原文写进审计日志。

反过来，如果新规则只约束附件数量，逐附件标签虽然足以判定，却多透露了哪些附件在同一次操作中相同。迁移工具会建议两端各记一个数量。两个方向合起来就能演示系统的作用：规则更改时发现漏证，核验目标变简单时减少留存。旧回执绑定当时的策略，这些清单用于未来发送。

## 一个人怎样验证

实验前将范围和对照写入本地提交 `70aa8f8`。策略比较、搜索、签发和验证沿用此前冻结的 `f15e621`。本轮选取一个单收件人本地邮件工具、审批和投递两个证据来源。全部策略都核验收件人，并分别核验附件内容、名称或长度的相等与包含，或者正文相等、附件份数上限。把 8 条规则两两切换，测完全部 56 个有向变更。去掉了对另一个人或另一个模型出题、标注、配置的依赖。[预定协议](protocol.md)

16 种邮件情形分别配 4 个正文长度模板，共 64 次本地 SMTP 投递。模板长度来自前期 ATBench 与 Claw 的四次发送调用，收件人、正文、附件和授权均为合成。批准快照在发送前写入审批表，取证端按 Mailpit 队列号通过 REST 读取实际发送，评分端另从邮箱数据库读取原始 MIME，按完整字段计算授权真值。两条路径共享同一个邮箱和审批事实。每条策略都在同样的 64 封邮件上判分，使存储量和覆盖可以成对比较。实验直接使用已核实的长度，不需要重新下载两套语料。[原始长度出处](../policy_transfer/results.json) · [本次逐策略与逐迁移数据](results.json)

| 同一批邮件，按 8 条策略分别计分 | 正确确定 / 512 | 错误或未知 | 认证日志字节 | 其中明文正文字节 | 其中明文文件名字节 |
|---|---:|---:|---:|---:|---:|
| 预设固定配置，支持全部八条规则 | 512 | 0 | 1,250,720 | 484,096 | 12,256 |
| 按当前规则生成配置 | 512 | 0 | 541,668 | 60,512 | 3,064 |

固定对照在两端记录收件人标签、逐附件内容标签、正文、文件名和字节长度。它也避免了明文收件人和附件原文。等权计算八条策略时，自动配置使完整日志小 **56.7%**，明文正文少 **87.5%**，明文文件名少 **75.0%**。正文只在核验正文的那一条规则中保留，文件名只在两条名称规则中保留。单独统计逻辑明文字节，完整字节另含 JSON 信封、操作标识、比较标签和认证码。同次操作的匹配关系、附件数量与重复模式也会披露。

| 56 个有向变更 | 个数 | 如何核验 |
|---|---:|---|
| 旧字段不足 | 46 | 每个变更都自动找到反例。92 次额外 SMTP 接收逐对证实“旧证据的可见信息相同、完整授权结论相反”。去重后共 8 对不同的邮件执行。 |
| 旧字段充分，另有披露排序更低的投影 | 6 | 例如已有逐项标签或完整名称列表，仅需核验份数时可以改记数量。 |
| 继续使用原字段 | 4 | 两种名称策略互换、两种长度策略互换，改变解释规则即可。 |

把旧字段配置直接用于下一批发送，在 56 × 64 个“规则变更 × 投递”判定中，有 1,672 个正确确定，另有 1,912 个证据不足。应用工具的增删清单后得到的字段逐项等于目标配置，3,584 个全部正确。该比较复用上述 64 次接收，反例重放另计。56 次变更是按设计穷举的组合，46/56 只描述这组规则，不能当作线上漏记率。

## 贡献边界与学期安排

已有研究给出了从程序合成数据最小化器的方法，已有邮件动作系统也展示了把附件哈希投影成数量的例子。本项目可具体检验的增量是**策略变更时跨两个独立证据来源推导采集差异，将缺证解释为可在实际邮箱复现的一对发送，并核验切换后的覆盖和隐私留存**。搜索在给定字段菜单、固定成本顺序和 12,544 个双源有限世界中核验充分性。日志节省受正文长度、策略使用比例和编码方式影响。论文可以据此论证系统在受控条件下的行为。真人使用体验与真实事故发生率都不属于验收指标。[数据最小化器合成](https://arxiv.org/abs/1611.05642) · [邮件动作字段投影](https://arxiv.org/html/2608.25474v1#A1.SS1)

按一个学期中的八个工作周安排，现有实现可直接复用。下表给出学生个人可以交付的材料。

| 时间 | 个人交付 | 完成标准 |
|---|---|---|
| 第 1–2 周 | 一页问题定义和信任边界图 | 说清谁批准、谁能证明实际投递、缺少回执时怎样判。 |
| 第 3–4 周 | 跑通编译器、迁移命令和本地演示 | 在自己的环境中演示整组相等改成允许部分发送，并读懂两封反例邮件。 |
| 第 5–6 周 | 复现实验并整理结果 | 从同一个 JSON 复核两种配置的覆盖与字节，解释至少一次漏证和一次可减记。 |
| 第 7–8 周 | 系统报告和五分钟演示 | 交付方法、结果表、局限和复现命令。其余学期时间可留给写作与修改。 |

## 复现和演示

在仓库根目录用 Python 3.10+ 安装仓库依赖。Mailpit 首次安装下载固定版本并校验，随后运行使用本地 CPU 和回环 SMTP。主实验在本机约 21 秒。只运行编译和迁移分析时无需启动邮箱。

```bash
python -m pip install -e '.[dev]'
python scripts/attachment_mail_backend.py --install --smoke
PYTHONPATH=src python scripts/run_solo_mail_audit.py --demo items_eq items_subset
PYTHONPATH=src python scripts/run_solo_mail_audit.py
cmp outputs/solo_mail_audit/results.json reports/solo_mail_audit/results.json
RUN_LOCAL_MAILPIT=1 PYTHONPATH=src python -m pytest
```

单独使用迁移工具时，通过 `--from-policy` 提供旧声明，或通过 `--current-fields` 提供现有的双端采集配置，再指定 `--to-policy` 和 `--capabilities`。输出的 `add` 和 `retire` 是未来回执所需的逐端改动。加 `--replay` 将在临时邮箱重放可用反例。完整目标策略不可核验时，工具报告这一结果并给出可用的失败见证。[迁移命令行](../../scripts/plan_mail_policy_change.py)
