# ATBench 和 Claw 发送日志里能找到哪些投递证据？

本次核对覆盖 90 条原始轨迹、91 次发送。要检验的命题是“本次操作是否实际把内容投递给未经用户批准的收件人”。这需要能绑定到该次发送的批准范围和实际投递状态。两套公开发布物提供轨迹记录、工具反馈与整轨迹标注。研究者能检查同一日志的前后印证程度，但无法独立读取当时的后台邮箱或审批快照。因此，这个命题在自然日志上的真实正确判定覆盖率及等覆盖下节省的查询数均**不可估计**。不可估计也不同于实验测出了零收益。[ATBench 数据发布](https://huggingface.co/datasets/AI45Research/ATBench) · [Claw 数据发布](https://huggingface.co/datasets/AI45Research/ATBench-Claw)

## 全量盘点

| 数据集及发送工具 | 轨迹 | 调用 | 记录中有工具反馈 | 反馈可以直接说明什么 |
|---|---:|---:|---:|---|
| ATBench `send_email` | 22 | 22 | 22 次相邻返回 | 22 个外层状态都是 success，14 次在结果对象含可识别状态字符串，11 次含 queued，1 次含 delivered |
| ATBench `send_sms` | 24 | 25 | 25 次相邻返回 | 25 个外层状态都是 success，22 次含可识别状态字符串，11 次含 queued，1 次含 delivered |
| Claw `sendMessage` | 28 | 28 | 28 次按调用 ID 和工具名绑定 | 28 次均标 `isError=false`；33 个文本块中 1 个可直接解析成 JSON 对象 |
| Claw `gog gmail send` | 16 | 16 | 16 次按调用 ID 和工具名绑定 | 16 次均标 `isError=false`；16 个文本块全为非 JSON 对象文本 |

ATBench 的状态词统计仅取 `result` 直接子字段，允许 `state`、`delivery_state`、`deliveryState`、`delivery_status`、`network_status` 与 `submission_status` 六种键的字符串值，大小写无关。一次调用可能出现两个不同状态。未计入的不等于状态缺失。Claw 的“绑定”是轨迹内调用身份的一致性。样本中也有工具返回等待确认或要求核实目的地，通用成功标志不足以判断最终状态。

## 下游读取是否补足证据？

脚本列出每次发送之后的所有工具名。根据工具名筛出直接的消息查询 `list_sms_messages` 与 `readMessages`，逐一核对三次返回。下表用固定版本、从零计数的行号定位。后续固定消息、添加反应等写操作没有计为消息查询。

| 样本 | 发送后的读取 | 能够核对的事实 |
|---|---|---|
| ATBench 第 450 行 | 查询短信列表 | 发送返回和后续列表条目具有相同消息 ID 与号码，列表条目还含投递时间。这是同一模拟轨迹内一条有明确键的二次读回。 |
| Claw 第 149 行 | 读频道最近消息 | 读回目标与发送目标的 ID 后缀一致，发送正文完整出现在列表文本中。这个匹配基于目标与文本，缺少唯一消息 ID 关联。 |
| Claw 第 93 行 | 读频道最近消息 | 工具报空列表，但读取目的地与发送目的地不同。空结果对原目的地的实际状态没有判别力。 |

上述观察支持把“拿到哪个系统的哪条记录，能否与同一发送匹配”列为方法输入。将三个二次读回例子用于日志适配和样例验证很合适。若要测真实投递判定，受控后端需要另外保存操作当时的授权、实际投递状态，并把查询接口与评分读取隔离。由同一日志的文字或整轨迹安全标签反推后台真值会改变所测命题。

## 复现

从仓库根目录运行。脚本先校验两个固定输入文件的 SHA-256，随后输出分工具计数、后续工具名和三条读回的行索引与匹配标志。输出省略原始收件人和正文。[核对脚本](../scripts/audit_natural_send_evidence.py)

```bash
PYTHONPATH=src .venv/bin/python scripts/audit_natural_send_evidence.py
```
