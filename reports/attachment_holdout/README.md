# 邮件附件授权留出实验

**冻结版没有通过新策略的迁移检验。** 原 CLI 不接受附件策略。把附件列表按内容排序后塞进现有的正文字段，会让旧的等值验证器误报 12 封合法邮件。加入外置的附件字段和多重集策略后，系统能自动找到四个必要的源端字段，与独立手写基线在相同的 72 次投递上判得一样准、存得一样少。它还能指出哪一端漏了什么，给出两封日志看起来一样、授权结论相反的邮件，并在实际邮箱上重现。[冻结协议](protocol.md) · [逐场景结果、配置和反例](summary.json)

## 实验如何取得真值

- **策略。** 对一封已由邮箱接受的邮件，实际 SMTP 信封收件人必须与发件前的有效批准相同。附件按 MIME 解码后的字节逐份比对。批准 A 两份才可以发 A 两份。允许少发、改名、调换顺序或改正文。给错误收件人的空附件邮件也越权。
- **系统边界。** 审批器先将授权快照提交到单独的 SQLite 表，再按配置签发证据。Mailpit v1.34.0 是独立的本地 SMTP 服务。投递取证端用 SMTP 分配的队列 ID 拉取 REST 消息，读取服务端写入的信封收件人和各附件内容。离线判定只读这两份带来源 MAC 的证据，无需比较密钥。计分器另按实验发起方分配的唯一 Message-ID 从 Mailpit 数据库读已提交的原始 MIME，用 Python 的解析器配合审批表逐份核对。两条路径共享 Mailpit 的收件事实和信封记录。这一后端支持的终态是“本地邮箱已接收并持久化”。[邮件适配器](../../scripts/attachment_mail_backend.py) · [Mailpit 固定版本](https://github.com/axllent/mailpit/releases/tag/v1.34.0) · [REST API](https://mailpit.axllent.org/docs/api-v1/)
- **样本来源。** ATBench 和 Claw 的前期切片共 91 次发送，仅 3 次有附件或路径引用。它们没有独立的附件字节和授权真值。本轮只取 ATBench send_email 的 16、810 字节以及 Claw gog gmail send 的 21、1,097 字节这四个可复核的正文长度。地址、附件、正文内容和授权均为合成。18 个预先写定的功能场景各在四个模板上运行，共 72 次本地投递，其中 44 次合法、28 次越权。四次重复不增加独立场景数。场景包括邮件头 To 与信封相反、同名同大小换内容、重复文件、零字节附件和最多五份附件。[源数据盘点](../send_log_pilot/natural_field_inventory.json) · [四个样本的选择代码](../../scripts/attachment_benchmark_shapes.py)
- **人工对照。** 独立代理看到策略和字段接口、在看编译器和结果前手写了专家配置、完整明文配置与四个有意不完整的配置。配置摘要与原编译器摘要在主实验前固定于提交 `efb0857`。没有招募真实开发者，没有测人工配置时间或实际部署中的错误率。[封存的配置](../../scripts/attachment_hand_configs.json)

## 同一批 SMTP 投递上的结果

“正确确定”为与独立真值相符的判定总数，分母包含证据不足。字节数为全部 72 对经认证回执的紧凑 JSON 大小。以下各行复用同一批邮箱提交。

| 配置 | 正确确定 / 72 | 误放 | 误报越权 | 证据不足 | 回执字节 |
|---|---:|---:|---:|---:|---:|
| 新增搜索器选出的配置 | 72 | 0 | 0 | 0 | 64,496 |
| 独立手写专家配置 | 72 | 0 | 0 | 0 | 64,496 |
| 完整明文手写配置 | 72 | 0 | 0 | 0 | 323,404 |
| 仅收件人和文件内容明文¹ | 72 | 0 | 0 | 0 | 236,572 |
| 收件人标签、文件名、大小、数量 | 20 | 0 | 0 | 52 | 59,000 |
| 收件人标签、数量、整袋内容标签 | 56 | 0 | 0 | 16 | 61,584 |
| 漏掉投递端逐附件标签 | 12 | 0 | 0 | 60 | 55,820 |
| 漏掉投递端收件人标签 | 20 | 0 | 0 | 52 | 58,520 |
| 收件人标签、附件数量 | 20 | 0 | 0 | 52 | 48,296 |
| 用旧版正文等值策略代判新策略 | 60 | 0 | 12 | 0 | — |

¹ 补充的大小敏感性对照。完整明文多留了 3,196 字节原始收件人、68,184 字节正文、1,772 字节文件名与 144,160 字节可恢复附件。自动配置和强手写的这四项均为 0。自动配置比完整明文总字节少 80.1%，比只保留策略所需原始输入少 72.7%。在附件只有 32 字节的最小模板，后一个对照用 13,351 字节，自动配置用 16,124 字节，多 20.8%。百分比随合成文件大小及序列化方式而变。业务邮箱需要持有原始邮件，实验结束时清理。上述数字仅指审计留存。

## 系统实际推导了什么

在授权端和投递端各提供六项候选，即收件人的原文或按操作生成的标签，附件原始内容、逐项标签、整袋标签或数量。搜索器枚举全部 4,096 个双端配置，在 400 个双端均有记录的有限世界里，检查同样的字段观察是否同时对应允许与越权。这个世界包含两个收件人、三种同名同大小的不同内容以及每端零到两份附件。784 个配置充分。按优先减少可恢复的附件内容字段、原始收件人字段、总字段数排序，唯一最优配置是两端各保留**收件人标签 + 逐附件内容标签列表**。每份标签随操作更换，列表保留重复次数。四项指字段类型，具体每封邮件的标签个数随附件数变化。操作编号、角色、协议版本、状态和 MAC 另计并已计入字节。[有限搜索器](../../scripts/attachment_schema_check.py) · [证据写入与验证](../../scripts/attachment_projection.py)

例如，批准同一人收 A、B。实际发 A 合法，换成同名同大小的 C 越权。在这两个世界里，收件人相等、文件数均为“批二发一”、整袋标签均不相等。对元数据或整袋配置，搜索器都建议在**两个来源**增加逐附件标签。若原配置只漏掉邮箱端收件人，修复仅需为邮箱增加一项。对四份不足的手写配置应用它给出的补字段方案后，72 次均判对。原本充分的两份手写配置无需补字段。删掉自动配置任一字段均能生成反例。把这些删除、手写遗漏和计数对照的 9 条反例路径逐条发到邮箱验证，共 18 次另行接收，去重后是 **3 对不同的反例**。每对保留字段的可见内容或相等关系一致，持久化 MIME 给出的授权结论相反。[反例重放](../../scripts/attachment_witness_replay.py)

另做一项只许从现有配置删字段的检验，直接考察多记了哪些敏感数据。在完整明文配置的 16,384 个子集中，最小配置由双端合计 14 项减至 4 项，两端各保留原始收件人和附件内容。强手写配置的 16 个子集中，没有一项能删。在一个事后构造的对照中，给强手写配置的两端各加上正文和文件名。遍历 256 个子集后，恰好删回这四项敏感字段，留存正文从 68,184 字节变为 0，文件名从 1,772 字节变为 0，认证记录从 140,912 降至 64,496 字节。三份精简结果均在同一批 72 次 SMTP 投递上保持完整正确覆盖。搜索模型预先声明正文字段在有限世界中恒定，同名同大小文件可有不同内容，这两种观测语义属于人工输入。主实验另用改名和正文变化的邮件验证所删字段确实不影响该策略。

在选定配置上另做 359 次回执故障检查。分别去掉审批回执、去掉投递回执、编辑收件人标签、换错来源密钥各 72 次，跨操作替换投递回执 71 次，均返回证据不足。这和审批来源明确签发“没有批准”、但邮箱已经收到邮件的 4 次越权不同。同次操作的收件人是否一致、附件数量和重复模式仍会披露。此设计依赖唯一操作号、可信的派发前审批、可信邮箱及受保护的比较和认证密钥。当前 MAC 适用于可信内部验证器。

## 对学期项目的判断

**可以把“部署前自动发现证据缺口并编译可复核的最小日志”定为系统贡献。** 最直观的演示是给系统一个看似合理的计数配置，让它交出一对无法区分的邮件、指出缺证的来源、生成修复，再用实际邮箱验证修复效果。先前研究已给出了数据最小化器合成。也有邮件动作系统把附件哈希投影成数量，因为其已知策略仅关心数量。本实验验证了策略改成“具体批准哪些附件”后，跨审批和投递两端如何识别并修复新出现的证据缺口。计数对照保留了精确收件人比较能力，测量的是这种投影在新任务上的适用性。[Data Minimisation: a Language-Based Approach](https://arxiv.org/abs/1611.05642) · [Field-Tier Minimization，附录 A.1](https://arxiv.org/html/2608.25474v1#A1.SS1)

**还差一次能决定泛化主张是否成立的实验。** 这轮事先冻结的 v1 只支持固定等值策略。新增的策略谓词、可比较的逐项投影、观测模型和运行时验证逻辑都由开发者为本次扩展编写。自动的是字段组合、必要性反例及补字段搜索。强手写与自动配置完全打平。建议接下来冻结同一套策略语言、搜索器与验证代码，由未参与实现的人给出下一条策略和强手写配置。以“只提交策略声明与能力说明即可得到结果”为通过条件，同时比较正确覆盖、明文留存、补记定位准确性及真实配置用时。一个人一个学期可把范围收在一个邮件后端、两种独立来源和两到三条策略，计算部分无需训练模型或调用付费 API。

## 复现

在仓库根目录，使用 Python 3.10+ 及仓库依赖，先按[前次实验](../atbench_claw_cross_tool_query_pilot_2026-11-18.md)准备两个固定校验和的数据文件。安装 Mailpit 的步骤需要下载固定版本的校验包，之后实验使用本机 CPU、回环 SMTP 与本地数据库。主报告只导出汇总和抽象反例。

```bash
python scripts/attachment_mail_backend.py --install --smoke
PYTHONPATH=src python scripts/run_attachment_holdout_pilot.py
RUN_LOCAL_MAILPIT=1 PYTHONPATH=src python -m pytest
```

本次独立重跑得到逐字节相同的聚合 JSON。包含实际 SMTP 用例的仓库测试全部通过（99 项）。运行器默认输出 `outputs/attachment_holdout/summary.json`。与[本次留档](summary.json)比较即可复核计数。原编译器固定在本地标签 `codex/send-log-v1-attachment-freeze`，每次运行都会重新校验源文件与手写配置的 SHA-256。
