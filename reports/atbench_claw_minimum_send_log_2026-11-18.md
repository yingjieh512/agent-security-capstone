# 发送越权核验要留下哪些证据？

在两个来源各自只为本地事实作证的条件下，审批方和投递方各保留一个**按操作生成的联合比较标签**，就足以核实实际投递的收件人和正文是否同时获批。若要进一步区分“收件人错误”和“正文错误”，两端还各需要一个收件人比较标签。这个区别决定了哪些隐私信息值得收集，也给系统提供了一个可以现场演示的功能。

本仓库已实现一个 Python 原型。给它审计策略与来源能力清单，它会输出可执行的字段配置；如果两种相反的执行结果在这些字段下看起来一样，它会输出这对反例。两端的写入函数按配置生成认证记录，验证函数只读取记录。完整 pilot 使用四种发送工具的参数，所有实际投递和审批历史都限定在本地重放。[实现](../src/trajectory_audit/send_log.py) · [配置与不可区分反例](send_log_pilot/compiled_schemas.json)

## 公共数据提供了什么

ATBench 的 send_email、send_sms 和 Claw 的 sendMessage、gog gmail send 共 90 条轨迹、91 次调用。按实际字段别名盘点，收件人含 CC/BCC 有 2,134 个 UTF-8 字节，正文有 20,248 个字节。另计主题、附件引用和无法拆开的供应商字段。80 次调用能保守地取出单一目的地和非空正文，来自 79 条轨迹，分工具为 19、20、28、13 次；它们的收件人有 1,497 字节，正文有 19,071 字节。统计单位是值的每次出现，不是去重后的个人数。[字段盘点](send_log_pilot/natural_field_inventory.json)

这些数据确证了输入形状和明文负担。其逐次可信审批快照及独立邮箱终态不可获取，因此历史发送是否真正越权无法逐条独立判分。下文使用这 80 份实际参数创建本地任务，用 SQLite 分别保存派发时的有效审批与权威投递终态。发出的证据分别来自对应表。计分器单独在两张表上做 SQL 比较。没有回执与权威确认未投递是不同状态。[上轮自然证据盘点](atbench_claw_natural_evidence_pilot.md)

## 最少字段与实测结果

对每次调用，审批状态有 5 种：明确无授权，或两种收件人 × 两种正文。投递状态也有 5 种：权威确认未投递，或同样的 4 种投递。两者交叉得到每次 25 种状态，每种策略共 2,000 个受控案例。每种策略都用同一组案例，不能将这些重放当作额外真实事故。若收件人和正文均不符，原因策略优先报告收件人错误。

| 核实目标 | 审批方保留 | 投递方保留 | 完整证据下的正确数 | 80 对日志总字节 |
|---|---|---|---:|---:|
| 是否向未经批准的收件人投递 | 收件人标签 | 实际收件人标签 | 2,000/2,000 | 45,360 |
| 实际投递的收件人、正文是否同时获批 | 获批二元组的一个标签 | 实际投递二元组的一个标签 | 2,000/2,000 | 44,560 |
| 还要区分无审批、收件人不符、正文不符 | 收件人标签 + 二元组标签 | 收件人标签 + 二元组标签 | 2,000/2,000 | 55,920 |

每一格的标签都是**源端认证的可空值**。审批方明确确认无授权、投递方明确确认未投递时，相应来源写入认证的 null。只要有可靠的未投递终态，就能单凭它排除该次“已经发生的未经批准投递”。缺源、等待或超时不能编码成 null。两条记录都须绑定同一唯一操作 ID、来源角色、协议版本、策略和配置摘要，并有各自的 MAC。表中最少的 2 或 4 个字段仅指内容投影，这些信封数据的体积都已计入总字节。

**强策略与原因策略的差异**可以直接复核。在收件人与正文均纳入授权范围时，如果只比较收件人，有 320 次正文不符会被错误放行。联合标签能检出这些不符，但在两项都存在而联合标签不相等的 960 次中，审计方看不出是哪一项不符。用这种最少记录回答原因问题，只能确定 1,040/2,000。增加两枚收件人标签后可确定全部 2,000 个原因。若两端接口只能分别计算收件人和正文标签，联合策略自动回退到四个字段。若投递端完全不能观察正文，编译器给出“同一收件人、审批不变、实际正文不同”的不足反例。[重放汇总](send_log_pilot/replay_summary.json)

## 隐私与大小

两端共享受保护的比较密钥，以 HMAC-SHA256 对版本、操作 ID、字段域以及规范序列化的字段值计算标签。二元组按有界结构编码，正文以原字符串的 UTF-8 内容比较。批准与投递的标签在同次操作上可比，不同操作的标签轮换。两端另外分别持有来源认证密钥。验证只需两个来源的 MAC 校验密钥，不需比较密钥。MAC 持钥者可以制作记录，这个原型适用于可信内部验证器；独立第三方不可抵赖性需要不同的认证方案。

- **明文留存。** 在每条原始参数分别被两端按原样批准和投递的 80 个重放中，完整明文基线在双端日志里留下 2,994 字节收件人和 38,142 字节正文。三个生成配置均为 0。这只衡量审计日志，业务邮箱和审批系统仍可持有原始数据。
- **记录总大小。** 用相同信封和紧凑 JSON 序列化，两个来源都记录收件人和正文原文是 84,120 字节；各记录一枚联合标签为 44,560，少 47.0%。作为强对照，当策略仅问收件人时，只记原始收件人的双端日志是 41,474 字节，用标签反而增至 45,360（+9.4%）。字段名字、MAC、ID 和转义都影响字节数。数值限定于当前编码、这批输入；不能作为磁盘空间下界。
- **可关联性。** 80 次调用中有 9 对跨操作的相同收件人。稳定标签暴露全部 9 对，用每次操作独立域的收件人标签做相等比较时命中 0 对。自然值切片没有重复正文或完整二元组，因而不能用它测这两类重复的关联改善。持比较密钥、能调用比较服务或有其他元数据的人可能仍能识别对象。同次操作的相等关系和显式空值也是披露。
- **故障。** 删除投递记录、挪用另一次操作的回执、修改认证字段或破坏 MAC，两个二元判定策略各有 2,000/2,000 返回证据不足。单独删除审批记录后，各有 400 个明确未投递的案例仍可判定，其余 1,600 个返回证据不足。这里的 400 来自设计的状态枚举，不是自然发送的取消率。

## 这里的“最小”如何核验

编译器当前支持三种预定义审计策略，考虑 18 个候选字段：每端的状态、原文、稳定标签、按操作生成的标签和联合标签。选择顺序优先避免正文原文、收件人原文和跨操作稳定标签，然后减少字段数；并列时选能区分的同次相等模式更少的配置。比较验证器在保留字段上能看到的相等关系，操作 ID 和 MAC 的随机字节不能当作分类信号。利用 25 个有限状态检查同一观察能否对应两个不同策略结果；对选出的配置，还枚举所有基数更小的字段组合，检查全菜单上的字段数最小性。删除任一选中字段后可给出一对标签相反且观察相同的具体状态。三种主配置都通过了这个检查。按真实账号名称作特殊决策、多个收件人、抄送、附件、别名解析、发送后撤销、流式或重复投递等需要扩展模型。

**基线界定了贡献。** 人工正确配置的两端比较标签也得到同样的正确率和字节数。另一个可信见证器若能看到双方的全部事实，只需持久化一位策略判定及认证信封，就能核实“该见证器作了何种判断”。该基线在两种二元策略下均答对 2,000 个案例；它不提供两来源的独立事实复核。字段最少的结论必须同时说明谁能看到什么、谁值得信任、审计者要回答哪个问题。

## 能否作为系统项目

**适合单人学期项目，初步证据支持的是“策略与来源能力决定日志配置”的系统设计。** 可演示的交付是配置编译器、两个受信源端写入函数、离线验证器和缺字段反例。切换二元核验与原因诊断会改变记录配置；撤掉投递端的正文能力，会让某些配置被拒绝。这是运行时会改变收集与留存行为的机制。

已有 agent 工作从动作声明生成披露和审计配置，数据最小化研究已有分布式输入表示的推导，目标导向日志也有长期研究。这里值得继续验证的增量是**从审计问题及相互独立的证据源能力编译出足够的投影，并为不可核实的能力配置生成反例**。本 pilot 的策略语言、工具适配和真值仍有限，尚不足以证明对已有方法的普遍优势。[Field-Tier Minimization](https://arxiv.org/abs/2608.25474) · [Monitoring Data Minimisation](https://arxiv.org/abs/1801.02484) · [Goal-Oriented Auditing and Logging](https://seclab.cs.ucdavis.edu/papers/tocs-96.pdf)

正式项目最有价值的验证是冻结编译器，接一套独立维护的本地邮件后端，留出一个此前没有实现的授权变化（如只批准指定的附件）。分别让开发者手配与系统生成日志，对比**能否找到不足配置、是否多留字段、跨策略错误判定、接入新来源所需工作量**。这能区分自动推导的价值与程序员本来就能写出的正确规则。

## 复现与使用

复用[上个 pilot 的数据下载与校验流程](atbench_claw_cross_tool_query_pilot_2026-11-18.md)。从仓库根目录运行，Python 环境须已安装仓库依赖。

```bash
PYTHONPATH=src python -m trajectory_audit.send_log --policy recipient_body
PYTHONPATH=src python -m trajectory_audit.send_log --policy explain
PYTHONPATH=src python -m trajectory_audit.send_log --policy recipient_body --omit '*.pair.*'
PYTHONPATH=src python -m trajectory_audit.send_log --policy recipient_body --capabilities reports/send_log_pilot/recipient_only_sink.json
PYTHONPATH=src python scripts/run_send_field_inventory.py
PYTHONPATH=src python scripts/run_send_log_minimization.py
PYTHONPATH=src python -m pytest tests/test_send_log.py
```

编译输出含所选字段、配置 ID、搜索范围和反例。在应用中把配置传给 issue()，由审批和投递适配器各自生成记录，再调用 verify()。本地实验的支持表只在内存 SQLite 中出现，导出的汇总文件不含地址、正文、比较标签或认证密钥。生产适配器需要稳定的收件人身份、唯一操作编号、权威终态及明确的审批快照；不能仅把公开日志返回的 success 当成独立投递证明。[用实际参数生成受控任务的脚本](../scripts/run_send_log_minimization.py)
