## 六篇深入核验：方法、资源与标签陷阱

### MRT — Reliable Weak-to-Strong Monitoring of LLM Agents

- Primary：[论文](https://arxiv.org/abs/2508.19461)；[代码](https://github.com/scaleapi/mrt)；[轨迹数据](https://huggingface.co/datasets/ScaleAI/mrt)。
- 方法：17 个 SHADE-Arena 任务对、15 个 CUA-SHADE-Arena 任务对；改变 agent 对 monitor 的知情程度和 monitor 对任务的知情程度。监控方案包括整段、层级摘要、顺序窗口摘要及二者分数混合；已经研究 human-in-the-loop escalation。因此“给长日志做摘要”“多视图混合”“弱模型监督强模型”本身不是新问题。
- 评估：AUROC 与 TPR@FPR≤1%；二者可能变化不一致。论文中的弱模型通常仍是商业模型 Haiku，不能直接等同于 0.6B/4B 本地模型。平均 unaware 轨迹约 10,100 tokens（CUA）和 25,100 tokens（SHADE）。
- 数据：HF 公共可访问，完整资源约 11.5GB，宜按任务下载子集。代码及数据 README 标注 CC BY-NC 4.0，第三方框架另有许可证；使用时核对具体文件。固定日志可离线重评，不需要重跑 agent 或 VM。
- **标签陷阱**：HF 的 `monitor_verdict` 是 monitor 预测，不是人工真值。官方 `notebooks/final/unaware_results_table.ipynb` 将 attacker transcript 目录赋 1、no-secondary-task 目录赋 0。论文理想目标是识别是否采取了追求恶意 side task 的行动，代码中的标签主要来自任务配置。不能不加说明地把“被布置恶意任务”视为“实际已违规”。建议以任务配置代理标签报告结果，另人工审计小规模子集。
- 数据切分：同一 task、原始轨迹、不同 monitor 结果及其不同格式版本不能随机分散到校准/测试两侧。代码分析片段已保存为 `mrt-analysis.py`。

### b³ — Breaking Agent Backbones

- Primary：[论文](https://arxiv.org/abs/2510.22620)；[Inspect eval](https://ukgovernmentbeis.github.io/inspect_evals/evals/safeguards/b3/)；[公开 weak 数据](https://huggingface.co/datasets/Lakera/b3-agent-security-benchmark-weak)。
- 方法：10 apps × 3 defense levels 的单步 agent-backbone snapshots，可隔离某一步 LLM 决策，不需要部署完整 agent。
- 资源：公开 weak 集可访问，共 630 条；论文选出的强攻击 210 条未全部公开。公开 weak 集平均攻击强度较低，不能据此宣称复现完整强集排行榜。
- 已覆盖：论文已比较较大集合、分层子集、去掉对源模型优化的攻击、较弱子集及不同聚合方式的排名稳定性。因此普通“小数据集保留模型排名”不是空白。
- 局限：单步 snapshots 无法验证攻击被检索到的概率、多步传播和真实系统整体安全；论文未完整测量 benign utility 和 latency。适合小规模静态 benchmark，但须把结论限定为 snapshot robustness。

### SafeToolBench

- Primary：[论文](https://arxiv.org/abs/2509.07315)；[GitHub](https://github.com/BITHLP/SafeToolBench)。
- 方法：1,200 条风险 instructions/tool plans，single-app 与 multi-app 各 600，四类风险；平均约 2–2.4 次 tool calls。工具、指令及二者组合分别进行风险评分，主方案阈值为 10。
- 资源：仓库公开包含 JSON 数据、API definitions、prompt 和 Qwen2.5-7B/GPT-4o 脚本；README 极简，需自己整理复现入口。抽查一个风险子集有 150 条，字段为 instruction、Risk category、explanation、output、quality_score。
- **不要误称没有 benign evaluation**：主 benchmark 是风险样本，但 Appendix C.1 用 800 条 AppBench 安全 instructions，其中 400 设阈值、另外 400 验证，并比较风险识别与安全样本保留的权衡。
- 局限：主要是合成 instructions/plans 及静态风险判断，没有执行整个现实工具流程。不能把计划判别准确率称为端到端安全率；一般个体偏好、授权上下文仍可能不足。适合静态 pre-call evaluator，小规模授权对照实验需要明确人工规范。

### MCPTox

- Primary：[论文](https://arxiv.org/abs/2508.14925)；[GitHub](https://github.com/zhiqiangwang4/MCPTox-Benchmark)。
- 方法：1,312 metadata-poisoning cases，45 个真实 MCP servers 的 353 个工具，主要评估单轮 tool-call 选择与参数。真实工具定义不等于每个实验都验证完整的真实服务执行。
- 资源：公共仓库包括 `pure_tool.json`、约 20MB `response_all.json` 缓存结果和 analysis notebook。README 仅标题，notebook 含作者本机绝对路径，需要清理数据入口。已有缓存适合 CPU 指标分析或小 guard 离线重评。
- **标签陷阱**：成功定义要求借用合法工具完成恶意动作；直接调用 poisoned tool 被分类为 Failure-Direct Execution，仍可能危险，不能转成“safe”。ASR 分母排除 invalid outputs，低 ASR 可能受能力失败影响。应分别报告 valid-output rate、benign-task following、拒绝及不同危险动作。
- 局限：单轮、半自动人工范式构造，未覆盖长期记忆或适应具体防御的攻击。新建攻击生成器不适合作为这个 solo capstone 的核心。

### MSB — MCP Security Bench

- Primary：[论文](https://arxiv.org/abs/2510.15994)；[GitHub](https://github.com/dongsenzhang/MSB)。
- 最新 ICLR 2026 版本：10 个模型、2,000 attack instances、12 attack types、25 servers、304 benign tools、405 attack tools、65 user tasks；注意这些数值可能不同于初版 abstract。
- 方法：覆盖 planning/invocation/response，检查工作区状态判定 attacker objective，使用调用日志识别用户任务所需工具的执行。
- 指标：ASR；PUA（攻击环境下用户任务完成）；NRP=PUA×(1−ASR)。**NRP 是两个边际量的乘积，不等于逐样本“任务成功且无攻击成功”的联合概率。** 用户工具被调用也不总等于最终任务完全正确，复用时需阅读任务级评分。
- Table 4：MCIP 防御平均 ASR 从 40.35% 到 28.69%，PUA 从 56.50% 到 48.91%，NRP 从 33.70% 到 34.88%。这支持同时分析安全与可用性，不能只看拒绝/攻击成功率。
- 资源与成本：有真实可执行 MCP tools、mcp-use/外部服务等依赖。全量运行对 10 周单人项目集成成本偏高；采用其 taxonomy 或现成静态工件更稳妥。

### MCPSecBench

- Primary：[论文](https://arxiv.org/abs/2508.13220)；[GitHub](https://github.com/AIS2Lab/MCPSecBench)。
- 最新 v3（2026-02）覆盖 17 类攻击，client/protocol/server/host 四个面，三个 MCP 宿主；不同宿主、传输协议、配置和模型共同影响结果。
- 资源：完整 playground，含 clients、servers、攻击脚本、GUI harness 和保护机制。适合作为 threat taxonomy，但完整复现涉及桌面宿主、协议和环境配置，不是单纯 GPU 推理任务。
- **标签/归因陷阱**：区分攻击成功、被安全机制主动拒绝和普通执行错误。某宿主攻击失败不能自动归因于模型安全；protocol/host 漏洞也不能作为小型 LLM guard 能解决的全部威胁。
- 本审计不建议将真实外部 MCP 生态扫描、宿主漏洞重现或完整端到端多平台防御作为 Colab MVP。

### A：轨迹压缩与授权证据保持

[TRACE: Trajectory Risk-Aware Compression for Long-Horizon Agent Safety](https://arxiv.org/abs/2606.00611)，[官方代码](https://github.com/Peregrine123/TRACE_official)，已经提出 Compressor–Reader 来保留稀疏、延迟和组合风险证据，也评估 Qwen3Guard-4B 等小模型。Reader 仍读取 raw trajectory + latent state，各方法 raw context budget 为 32k。论文明确不声称推理更省内存/延迟，其附录报告 TRACE 的 peak memory 31.91GB。MRT 则已经研究层级/顺序摘要。

因此可做的准确问题是：**固定实际输入 token budget 下，冻结小 guard 对授权证据丢失有多敏感；确定性保留授权、动作、数据来源/去向的 spans 是否比等长截断或普通摘要更可靠？** 把成果定位为可复现实证审计与小型工具，不宣称首个安全证据压缩器。

最低设计：300–600 条基础轨迹；1–2 个数据集；1k/2k/4k budgets；full（可运行参考）、head+tail、普通摘要、规则证据保留四种表示。人工审计授权相关小子集，按原始 task/trajectory 切分。测 paired flips、unsafe recall/FNR、benign FPR、证据 retention、tokens、latency、peak VRAM。删除或改变授权会改变可判定信息，不能自动沿用原标签。小样本宜先报告 5% FPR operating point 及置信区间，不宣称已证明 1% FPR。

### B：等价表示的分歧是否有助于弃权

公开稿 [View-Disagreement Escalation for Robust Web-Agent Trajectory Judges](https://lemma-public-asset.analemma.ai/online/fars/live/live_live_20260213/idea_ed555e4e-a31d-4e17-a0ef-e1ba09213e4f/main.pdf) 第一页明确标注由 FARS/Analemma automated research system 生成；未确认同行评审。它已经使用有/无 CoT 的两视图分歧，触发更严格 rubric；使用 70B judge，评估 AgentRewardBench task success/failure。有/无 CoT 并非信息等价，目标也不等于安全。应把它列为已有公开想法，不能据此接受其实验数字为可靠定论。

仍可做：**对完全保留事实、角色和事件顺序的 lossless serialization，小 guard 的格式间分歧能否优于单次 confidence 和等成本重复采样，预测安全漏检？** 使用可逆 JSON/role-block/key-order 表示，round-trip 验证字段和值；自由改写和删除 CoT 不算等价变换。比较 error-detection AUROC/AUPRC、risk–coverage/AURC、同 coverage 下 FNR/FPR、正确案例弃权率和总 token/耗时。必须匹配推理预算；一致地犯错仍无法由分歧检测，不能把一致性当正确性证明。建议作为 A 的可选第二实验，而不是扩成独立大项目。

## 算力与交付建议

已核验可访问的官方模型：[Qwen3Guard-Gen-0.6B](https://huggingface.co/Qwen/Qwen3Guard-Gen-0.6B)、[Qwen3Guard-Gen-4B](https://huggingface.co/Qwen/Qwen3Guard-Gen-4B)、[Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)。选其中两个冻结 checkpoint，batch 1、限制 context、固定量化配置即可；T4 的实际吞吐与长上下文可行性须先用 30–50 条 pilot 实测。内容安全 guard 并非原生 agent trajectory guard，领域错配需要在解释结果时说明。

10 周建议：1–2 周数据/标签审计和 pilot；3–4 周实现可验证的表示与证据变换；5–6 周固定主实验；7–8 周分歧/弃权和必要消融；9–10 周统计、error taxonomy、复现包与报告。核心是给出可靠的实证边界；无需预设产生新 SOTA。不要把量化、跨语种、训练和在线 agent 环境同时纳入本项目。
