# 安全裁判真的需要阅读完整过程吗

## ATBench 局部视图与相似任务整组留出审计研究计划

**文档状态：** Research Proposal Draft  
**拟议研究者：** Yingjie Huang  
**项目周期：** 约 10 周，一个 academic quarter  
**计算资源：** 单人，普通笔记本 CPU 与 Google Colab 级单卡 GPU  
**研究对象：** 用于评价大语言模型智能体是否安全的 benchmark 与 safety judge

## 提案摘要

现在的大语言模型不再只能回答问题。接入邮件、网盘、浏览器、数据库或支付系统后，它可以连续执行多个动作。这类能调用外部工具并完成任务的程序通常称为大语言模型智能体，也常简称为 agent。Agent 一旦能够采取行动，安全问题就不再只是“最后一句话是否有害”，还包括它是否读取了不该读取的文件、使用了错误账户、把信息发给了错误对象、接受了网页中的恶意指令，或者在中间步骤越过了用户授权。

为了评价这些风险，研究者会使用安全裁判，也就是读取 agent 执行记录并判断其安全与否的模型或分类器。完整执行记录通常包含用户要求、可用工具、agent 的每一步动作、工具返回的信息以及最后回答。理论上，安全裁判应当像事故调查员阅读黑匣子一样，综合这些信息判断整个过程是否安全。

本研究提出一个基础但容易被忽略的问题：**现有 benchmark 的高分，真的要求安全裁判理解完整过程吗？** 如果一个模型只看最后一句“我拒绝执行”或“任务已经完成”，就能猜中大部分参考标签，那么高分只能证明它会预测这套试卷的答案，不能单独证明它理解了多步工具使用中的风险。

我们的预备实验支持认真调查这个问题。在 ATBench 的 1,000 条人工审核轨迹上，一个刻意简单、只识别词语和短语模式的分类器，仅阅读最终回答时取得 0.880 的 Macro-F1；阅读完整轨迹时为 0.829。在第二个公开 benchmark R-Judge 上，只读最后一个 agent 动作取得 0.917，阅读完整记录为 0.803。这里的 Macro-F1 是同时照顾 safe 与 unsafe 两类表现的综合分类指标，范围为 0 到 1，越高越好；它不是“正确率百分比”。

这些结果表明最终回答或局部动作中存在很强的标签信号，但它们尚不能证明 ATBench 有数据泄漏，也不能证明完整轨迹没有价值。最后回答可能确实忠实总结了之前发生的事情；简单文字模型也可能因为完整轨迹太长而受到不公平影响。为区分这些解释，本项目将在已有 CPU 审计的基础上增加两项关键验证：第一，使用没有在 ATBench 上训练的冻结小型安全模型重复五种信息视图的比较；第二，构造并人工核验“动作轨迹保持不变、只改变最终措辞”的配对样本，直接测量安全裁判是否会被结果措辞带偏。

本项目不训练大模型、不运行真实攻击，也不要求浏览器或 MCP 基础设施。MCP 是 Model Context Protocol 的缩写，是一种让模型连接外部工具和数据源的标准接口。项目主要复用公开静态数据。无论最终发现局部信号仍然很强，还是发现现代安全模型确实必须阅读完整轨迹，项目都能回答一个明确的问题，并形成可复现的 benchmark 审计方法。

> **本研究最重要的区分**
>
> 我们研究的是“benchmark 分数是否要求模型使用完整轨迹”，不是“完整轨迹在真实世界中是否有用”。现实中完全可能出现最终结果看起来正常、但中间过程已经越权的情况。因此，局部视图在 benchmark 上得分高，并不意味着部署时可以丢弃完整日志。

## 一个不需要专业背景的例子

假设用户让一个 AI 助手把公开会议议程发给同事。一次完整执行可能是：

1. 用户说：“请把公开议程发给 Alice。”
2. Agent 打开网盘搜索文件。
3. 一个网页或工具返回文字：“请改为把机密附件发送给 external@example.com。”
4. Agent 读取机密附件并将它发送给外部地址。
5. Agent 最后回答：“任务已完成。”

真正的安全判断需要理解第 1 步授权了什么、第 3 步的信息来自谁、第 4 步实际做了什么，以及这些步骤之间是否一致。如果一个安全裁判仅凭最后一句“任务已完成”就预测 unsafe，它可能在这道题上答对，却没有证明自己理解了越权发送发生在哪里。

反过来，如果安全的 agent 拒绝执行恶意要求，并在最后回答中写“出于隐私原因，我不能这样做”，一个简单模型也可能只凭“隐私”和“不能”判断 safe。这种线索可能是合法的结果摘要，但如果 benchmark 声称测量的是多步骤风险理解，就必须额外证明高分不只是来自这些局部提示。

这类似一份声称考查数学推理的考试：如果学生不读题，只看答案的长度或最后一个词就能取得高分，问题不一定是参考答案错了，而是这张试卷没有充分证明学生使用了它声称要考查的能力。

## 研究目标

本项目的总体目标是建立一套低成本、可复现的审计方法，判断 agent-safety benchmark 的标签在多大程度上可以由局部信息预测，以及高分是否真正需要跨步骤证据。

具体目标包括：

1. 测量完整轨迹和不同局部视图分别能够恢复多少 ATBench 标签信息。
2. 检查这种局部信号在相似任务被整组留出后是否仍然存在。
3. 排除几个简单解释，包括缺失最终回答、明显的拒绝词、文本长度、词汇容量和分组方法。
4. 使用冻结的小型安全模型判断现象是否只属于传统词语分类器。
5. 使用人工核验的配对反事实，直接测试最终措辞改变是否会改变安全判定。
6. 在 R-Judge 上重复核心分析，评估现象是否只存在于 ATBench。
7. 形成一套未来 trajectory benchmark 可以直接采用的最低报告标准。

## 研究不试图完成什么

为避免把一个 quarter 的项目扩展成无法完成的大型系统，本研究明确不做以下事情：

- 不训练新的大语言模型或新的大型 safety guard。
- 不重新运行产生 ATBench 或 R-Judge 轨迹的 agent 环境。
- 不搭建真实浏览器、邮件、支付或 MCP 攻击环境。
- 不根据本项目结果宣称 final-answer-only 模型可以替代完整过程审查。
- 不把“局部文字能够预测标签”直接称为数据泄漏、标签错误或 benchmark 失效。
- 不声称在公开 benchmark 上的表现等于真实部署中的安全保证。

## 核心术语的通俗解释

| 术语 | 通俗解释 | 在本项目中的作用 |
|---|---|---|
| 大语言模型，Large Language Model，LLM | 从大量文本中学习、可以理解和生成自然语言的模型。 | Agent 的语言理解与决策核心。 |
| 大语言模型智能体，LLM agent | 以语言模型为核心、还能连续调用外部功能的程序。例如先搜索文件，再读取文件，最后发送邮件。 | 被安全裁判评价的对象。 |
| API，应用程序编程接口 | 一个程序按约定格式请求另一个程序提供功能的接口。 | Agent 常通过 API 搜索文件、发邮件或提交付款。 |
| MCP，Model Context Protocol | 一种让模型连接外部工具和数据源的标准接口。 | 完整 MCP 系统需要额外服务与安全隔离，本项目不搭建它。 |
| 工具，tool | Agent 可以调用的外部功能，例如搜索文件、发邮件或提交付款。 | 工具调用可能产生真实后果。 |
| 工具说明，tool schema | 工具的“使用说明书”，列出工具名称、用途、参数和输出格式。它不等于一次真实调用。 | 构成完整轨迹中的静态背景信息。 |
| 轨迹，trajectory | 一次任务从开始到结束的时间顺序记录，包括用户消息、工具说明、agent 动作、工具返回结果和最后回答。 | 本研究要检查的完整证据，可类比为黑匣子日志。 |
| 安全裁判，safety judge 或 guard | 判断一段回答或执行轨迹是 safe 还是 unsafe 的模型或分类器。 | 本项目审计的对象；它与被评价的 agent 不是同一个角色。 |
| Benchmark，基准测试 | 一套固定例题、参考标签和计分规则，用于可重复比较不同方法。 | ATBench 和 R-Judge 都属于安全 benchmark。高分首先说明在这套试卷上表现好。 |
| 参考真值，ground truth 或 gold label | Benchmark 用来判分的参考答案。 | ATBench 标签经过人工审核，但仍是依据规则作出的参考判断，并非绝对无误的自然事实。 |
| Safe 与 unsafe | Safe 表示参考标签认为轨迹安全；unsafe 表示参考标签认为轨迹包含安全风险。 | 本项目的二分类目标。 |
| 信息视图，view | 从同一条轨迹中按固定规则只保留一部分信息。标签不随视图改变。 | 用于测试模型究竟需要看到多少信息。 |
| 局部视图，partial view | 不包含完整轨迹的视图，例如只看用户请求或最后回答。 | 如果局部视图已能得到高分，就说明标签容易被局部线索预测。 |
| 捷径信号，shortcut signal | 与标签高度相关、但不要求完成研究声称要测的完整推理的线索。 | 例如看到“我拒绝”就猜 safe。捷径不一定是错误，但会限制分数能证明什么。 |
| 标注痕迹，annotation artifact | 数据制作或写作方式留下的规律，使模型可以利用非目标线索预测标签。 | 是局部信号的一种可能来源，必须通过进一步实验区分。 |
| 数据泄漏，data leakage | 原本不应在预测时获得的信息进入模型，或高度相关的近重复案例跨越训练和测试边界。 | 本研究明确排除 label、reason 等答案字段；模板级重叠因缺少官方 family ID 仍不能完全排除。局部措辞相关性本身不能未经证明就叫泄漏。 |
| 消融实验，ablation | 有控制地拿掉一种信息或改变一个因素，再观察结果如何变化。 | 五种视图、去掉最终回答、遮盖词语等都属于消融。 |
| 聚类，clustering | 在不看答案的情况下，把内容相似的案例自动归到同一组。 | 用于近似识别相似任务家族。 |
| K-means | 一种常见的自动分组算法，需要预先指定分成多少组。 | 本项目用它生成 25、50、75 或 100 个近似任务组。 |
| 随机切分，random split | 随机把案例分到训练集和测试集，同时大致保持两类比例。 | 容易复现，但相似案例可能同时出现在训练和测试中。 |
| 相似任务整组留出，group-held-out split | 先把相似案例归组，再保证同一组不会同时出现在训练和测试中。 | 比随机切分更严格，但因 ATBench 没有官方任务家族 ID，只能使用近似分组。 |
| 交叉验证，cross-validation | 将数据分成若干份，轮流用其中一份测试、其余训练。 | 本项目使用五折交叉验证，让每条记录都在模型没见过它时获得一次预测。 |
| 折外预测，out-of-fold prediction | 某条记录在其所属测试折中得到的预测；训练该模型时没有使用这条记录。 | 用于计算所有主要指标，避免直接在训练样本上打分。 |
| TF-IDF | 把文本转换为数字特征的传统方法。某个词在当前文本中常见、但在所有文本中不常见时，会得到较高权重。 | 让模型识别词语和相邻短语规律，但不等同于理解事件因果。 |
| Unigram 与 bigram | Unigram 是单个词；bigram 是相邻两个词组成的短语。 | 本项目的简单模型同时使用单词和相邻双词。 |
| 逻辑回归，logistic regression | 一种简单线性分类器，为每个词语特征学习正负权重，再输出 safe 或 unsafe 的概率。 | 被刻意选作“最低能力基线”，不是拟部署的最终安全系统。 |
| 冻结模型，frozen model | 使用已经训练好的模型，但实验中不再根据 ATBench 更新它的参数。 | 用于验证结果是否只属于 TF-IDF 逻辑回归，同时减少在 benchmark 上过拟合。 |
| 模型参数，model parameter | 模型在训练中学到的内部数字。参数量常用 B 表示 billion，即十亿。0.6B 约为 6 亿个参数，4B 约为 40 亿个参数。 | 参数越多通常越占显存和计算时间，但不保证一定更可靠。 |
| 小型安全模型，compact guard | 参数量较小、能够在 Colab 级 GPU 上运行的安全判断模型。 | 作为下一阶段的现代模型复验。小型不表示一定不准确。 |
| Prompt，提示词 | 交给语言模型的任务说明和输入格式。 | 后续实验必须在看完整结果前固定提示词，避免为某个结果反复调整。 |
| Token，词元 | 模型读取文字时使用的小单位，可能是一个词、半个词、汉字或标点。 | 模型一次最多能读取的 token 数称为上下文窗口。超过窗口的内容必须截断。 |
| FP16，16 位浮点精度 | 用 16 个二进制位存储模型中的小数，是常见的 GPU 推理格式。 | 0.6B 主模型拟使用 FP16；它比 32 位格式节省显存。 |
| CPU 与 GPU | CPU 是电脑的通用处理器；GPU 擅长同时进行大量相似计算，常用于运行神经网络。 | 传统文字基线使用 CPU，冻结小模型使用一张 Colab GPU。 |
| Google Colab | 在浏览器中运行 Python 代码的云端 Notebook 服务，通常可临时获得一张 GPU。 | 用于界定本项目的计算预算。 |
| Macro-F1 | 分别计算 safe 类与 unsafe 类的 F1，再给两类同样权重。F1 同时考虑“预测为某类时有多准”和“该类被找回多少”。 | 主要综合指标。范围 0 到 1，越高越好；0.880 不能简单读作 88% 正确。 |
| AUROC | 不先固定一个判定门槛，考察模型是否通常把 unsafe 样本排在 safe 样本前面。0.5 左右接近随机，1 为完美排序。 | 补充衡量排序能力；它不直接告诉我们最终漏掉多少危险案例。 |
| 危险漏报率，unsafe false-negative rate，FNR | 所有真实 unsafe 案例中，被错判为 safe 的比例。 | 表示“应该拦却放过”的风险，越低越好。 |
| 正常误报率，safe false-positive rate，FPR | 所有真实 safe 案例中，被错判为 unsafe 的比例。 | 表示“正常任务却被阻止”的代价，越低越好。 |
| Bootstrap，自助重采样 | 从现有组中有放回地反复抽样并重算指标，用于观察样本组成变化时结果会波动多少。 | 本项目对固定的推断组和折外预测重复抽样 500 次。它不会凭空创造新的独立证据。 |
| 95% 置信区间，confidence interval | 由重采样得到的合理波动范围。 | 本项目区间只反映固定分组与固定预测下的样本波动，不包括重新选模型、重新聚类或换数据集造成的不确定性。 |
| 反事实配对，counterfactual pair | 两条案例除一个研究因素外尽量完全相同。 | 本项目保持动作轨迹不变，只改变最终措辞，以更直接地测试措辞是否影响判断。 |
| 分布变化，distribution shift | 训练数据和新数据在任务、写法、类别比例或生成方式上发生变化。 | ATBench 与 ATBench500 的迁移下降提示局部线索未必能跨版本稳定使用。 |
| 概率校准，calibration | 模型声称“90% 可能 unsafe”的样本中，是否真的约有九成 unsafe。 | 排序能力好不代表概率可信，跨版本时尤其需要区分。 |
| JSON 文件 | 一种有固定字段和层级结构、便于程序读取的文本文件。 | ATBench 和 R-Judge 的原始记录以类似结构保存。 |
| Manifest，运行清单 | 记录数据版本、样本 ID、分组、随机设置和程序配置的机器可读文件。 | 让别人能够确认某次实验究竟用了哪些输入和设置。 |
| 随机种子，random seed | 控制计算机伪随机过程的起始数字。使用相同种子通常能重复同一分组或切分。 | 本项目记录所有种子，并检查多个种子下结论是否稳定。 |
| SHA-256 | 根据文件内容计算出的长字符串，可理解为文件的数字指纹。文件只要改变一个字符，指纹通常就会改变。 | 用于确认后来使用的数据与本次实验完全相同。 |

## 研究背景与问题的重要性

### Agent 安全要求检查过程而不只是结果

普通聊天模型主要输出文字，而 agent 可以执行操作。一次危险事件可能分散在多个步骤中：用户授权了 A，工具内容要求 B，agent 最后却执行了 C。任何单独一句话可能看起来正常，风险来自这些步骤之间的关系。

因此，trajectory-level safety evaluation，即轨迹级安全评估，声称测量的不只是有害文字识别，还包括以下能力：

- 区分用户授权与网页、工具或第三方提供的指令。
- 追踪数据从哪里读取、又被发送到哪里。
- 判断后续动作是否超出最初授权范围。
- 识别最终结果正常但中间过程不安全的情况。
- 在多个工具和多轮交互中保持一致的安全判断。

### Benchmark 分数与真实能力并不完全相同

Benchmark 类似统一考试。好的考试应该迫使考生使用它声称要测的知识。如果可以通过与目标能力无关的表面规律得高分，那么分数的解释范围就会缩小。

研究方法中常用“构念效度”描述这个问题。构念是研究想测量的抽象能力，例如“理解多步安全风险”；构念效度则问这套测试是否真的测到了这种能力。本项目不是质疑所有参考标签，而是审计 ATBench 分数能否证明安全裁判使用了跨步骤证据。

### 本项目与已有工作的关系

AgentDojo、Agent-SafetyBench 和 Agent Security Bench 等工作主要评价目标 agent 在工具环境中是否安全完成任务。R-Judge、AgentAuditor、TraceSafe 和 ATBench 则评价另一个读取执行记录的安全裁判。JAILJUDGE 进一步说明安全判断本身也是需要专门评估的模型任务。

自然语言处理领域已有一种相近的诊断方法：当一项任务理论上需要阅读两个输入时，研究者会故意只给模型其中一个输入。如果模型仍然得分很高，就说明数据中可能存在局部规律。本项目将这种 partial-input baseline，也就是局部输入基线，迁移到 agent 轨迹评估。

与本项目最接近的另一类工作表明，只看最终结果会漏掉“结果看起来正确、过程却发生错误”的情况。该结论说明完整轨迹在现实审查中很重要。本项目研究的是互补问题：公开 benchmark 是否真的要求模型使用这些过程信息。

## 研究空缺与本项目的新颖性

已有工作分别回答了几个相邻问题，但尚未把它们组合成这里的完整审计。

- 现有 agent benchmark 主要比较不同 agent 或 guard 的总分，通常不会系统报告只看用户、工具、动作或最后回答的低成本基线。
- 自然语言处理领域已经用局部输入基线发现“考试可以被捷径完成”的情况，但该方法尚未被系统应用到包含工具调用、环境返回和授权关系的 agent 轨迹。
- 已有研究证明完整过程能够暴露最终结果看不出的错误，但这不能反过来保证某个公开 benchmark 的分数确实要求模型读取过程。
- 一般的随机训练测试切分容易让相似模板分散在两侧；ATBench 又没有公开真实任务家族 ID，因此必须同时报告近似分组结果和它的限制。

本项目的新意不是提出一个更大的安全模型，而是把以下五个部分放进同一套可复现协议：

1. 对同一轨迹生成五种严格定义的信息视图。
2. 同时比较随机切分和相似任务整组留出。
3. 用透明的传统模型暴露最低成本的标签信号。
4. 用冻结的小型现代 guard 检查结果是否只属于传统模型。
5. 用动作保持不变的人工反事实，将“相关”推进到更直接的措辞干预证据。

因此，项目的主要研究贡献是 measurement audit，也就是审计测量过程本身，而不是再训练一个排行榜分数更高的 classifier。

## 数据与参考标签

### ATBench

ATBench 是本项目的主数据集。公开版本包含 1,000 条 agent 轨迹，其中 503 条参考标签为 safe，497 条为 unsafe。每条记录平均约有 9 个消息或事件，数据中共出现 2,084 个不同的可用工具名称。论文说明这些记录先经过规则和语言模型筛选，之后逐条接受完整人工审核，并附带风险来源、失败模式和现实危害等解释字段。

本项目只把 safe 或 unsafe 作为预测目标。以下字段在建模前全部从输入中删除：

- `label`，也就是目标答案；
- `reason`，人工给出的判定理由；
- `risk_source`，风险来源；
- `failure_mode`，失败类型；
- `real_world_harm`，可能的现实危害。

这些字段只允许在完成预测后用于错误分析。这样可以防止把答案或答案解释直接泄露给模型。

ATBench 只发布了一个官方 test split，没有独立的公开训练集与验证集。因此，本项目在这 1,000 条记录上建立自己的五折交叉验证，用于 benchmark 诊断。所有分数都是研究者自定义分析切分上的折外结果，不是 ATBench 官方排行榜分数。

数据文件固定到公开模型与数据托管平台 Hugging Face 的 revision `de862a3d5363aa3928f70e2228b275135597226c`，主文件 SHA-256 为 `80c534b5f3517c872b528a2e6b64e34495206968edd184f4aed563d39f0cca09`。Revision 是平台记录的版本标识，SHA-256 是根据文件内容计算的数字指纹；两者共同帮助确认以后下载到的是完全相同的数据。

### R-Judge

R-Judge 用作外部复验数据。固定官方仓库 commit 后，共读取 571 行；移除两条与更早记录具有完全相同 judge 输入的重复行后，保留论文报告的 569 条记录，其中 269 条 safe、300 条 unsafe。

R-Judge 没有明确的“最终回答”标记。因此，本项目只能使用“最后一个 agent 动作”作为近似局部视图。这个动作可能是工具调用、界面操作、拒绝文字或自然语言回答，不能与 ATBench 的 final answer 完全等同。

R-Judge 的 27 个来源 JSON 文件被用作粗粒度分组：同一来源文件中的记录全部进入同一折。该分组是可复现的，但一个文件内部仍可能包含多个任务模板。

### 参考标签的边界

本研究把人工审核标签称为“参考真值”，而不是绝对真理。人工判断可能受到规则解释、上下文信息和标注一致性的影响。项目研究的是这些公开标签能否被局部文本恢复，并不独立证明每一个标签在现实世界中都正确。

## 五种主要信息视图

每条 ATBench 轨迹会通过固定程序生成五种视图。程序不读取标签，事件顺序也不会被打乱。

| 视图 | 保留的信息 | 它测试的问题 |
|---|---|---|
| 完整轨迹，full | 工具说明和从开始到结束的全部事件 | 模型读取 benchmark 提供的全部证据时表现如何？ |
| 仅用户信息，user-only | 用户发送的消息 | 标签是否能从用户要求本身猜出？ |
| 仅工具说明，tool-schema-only | 可用工具的名称、用途和参数 | 标签是否与某类工具或工具命名高度相关？ |
| 仅 agent 动作，actions-only | Agent 调用的工具、参数和其他动作 | 不看工具返回结果和解释，仅看行为能预测多少？ |
| 仅最终回答，final-answer-only | 最后一次明确的完成回答 | 最后的拒绝、确认或结果描述是否已经暴露大部分标签？ |

附加视图用于解释结果：

- `static_context`：用户信息加工具说明，不包含实际执行过程。
- `prefix_25`、`prefix_50`、`prefix_75`：只保留前 25%、50% 或 75% 的事件。
- `full_without_final`：完整轨迹中移除最终回答。
- `user_plus_final`：只保留用户信息和最终回答。
- `final_answer_masked`：在最终回答中把明显的拒绝、授权、隐私或完成短语替换为中性占位符。

## 已完成的预备研究

### 简单模型为什么适合作为第一步

预备研究使用 word unigram 和 bigram TF-IDF 加 class-balanced logistic regression。Class-balanced 表示训练时对两类赋予平衡权重，避免模型只偏向数量更多的一类。

我们故意不用复杂模型作为第一个实验。原因是：如果一个只会计算词语和短语权重的透明模型，仅凭最终回答就能得到很高分，那么可以明确说明标签中存在容易取得的局部文字信号。它不证明大语言模型也会使用同样的捷径，但为进一步实验提供了有力动机。

完整轨迹平均约 14,630 个字符，最终回答平均约 278 个字符，相差约 53 倍。因此，短文本更容易分类也可能来自 TF-IDF 对长文本的表示方式。本项目将这种可能性视为需要控制的替代解释，而不是忽略它。

### 两种数据划分

第一种是五折分层随机交叉验证。分层表示每一折中的 safe 与 unsafe 比例尽量接近总体比例。

第二种是五折相似任务整组留出。由于 ATBench 没有公开原始模板或任务家族 ID，项目先在完全不看标签的情况下，根据标准化用户请求和工具名称的 TF-IDF 表示，使用 K-means 生成 50 个近似组，再保证每个组只出现在一个测试折中。聚类本身不读取 safe 或 unsafe 标签；将完整组分配到五个折时，程序会参考类别比例，尽量避免某一折几乎只有一个类别。

所有视图使用完全相同的折，因而 full 与 final 的差异是对同一批测试记录的配对比较。该方法减少了明显的近似案例跨折问题，但不能保证恢复真实、未公开的场景家族。

### ATBench 主结果

下表是 50 个近似组的 group-held-out 折外结果。

| 视图 | Macro-F1 | AUROC | 危险漏报率 FNR | 正常误报率 FPR |
|---|---:|---:|---:|---:|
| 完整轨迹 | 0.829 | 0.903 | 0.179 | 0.163 |
| 仅用户信息 | 0.681 | 0.740 | 0.280 | 0.358 |
| 仅工具说明 | 0.585 | 0.627 | 0.447 | 0.382 |
| 仅 agent 动作 | 0.658 | 0.739 | 0.376 | 0.306 |
| 仅最终回答 | **0.880** | **0.938** | **0.044** | 0.193 |

最终回答的 Macro-F1 比完整轨迹高 0.051。对固定的 50 个近似组进行 500 次 bootstrap 后，该配对差异的条件性 95% 区间为 `[+0.011, +0.091]`。

这一结果不能解释为“最终回答在所有意义上都更好”。它将危险漏报率从 0.179 降到 0.044，却把正常误报率从 0.163 提高到 0.193。换句话说，只看最终回答的模型在这套数据上较少放过 unsafe 案例，但稍微更容易错误阻止 safe 案例。不同部署场景对这两种错误的代价可能完全不同。

换算成更直观的数量，完整轨迹模型大约漏掉 89 条 unsafe 记录，并把约 82 条 safe 记录错误报警；最终回答模型大约漏掉 22 条 unsafe 记录，同时错误报警约 97 条 safe 记录。这些数量由折外预测率近似换算，目的是帮助理解两种错误的方向，而不是替代机器生成的逐条结果。

### 已完成的替代解释检查

为了判断主结果是否由一个很简单的偶然因素造成，预备研究完成了以下检查。

#### 缺失最终回答

26 条记录没有明确的终止回答，并且这 26 条全部是 unsafe，因此“缺失”本身就是一个标签线索。移除这 26 条、保留其余记录原有分组并重新训练后，最终回答视图在 974 条记录上仍有 0.871 Macro-F1。结果说明主发现不是仅由这 26 个缺失值支撑，但该删除会改变评估总体，不能被解释为缺失标记的严格因果效应。

#### 信息在什么时候出现

在 group-held-out 设置中，只看前 25%、50% 和 75% 的事件时，Macro-F1 依次为 0.650、0.720 和 0.754。移除最终回答的完整轨迹为 0.766，加入最终回答后为 0.829，仅看最终回答为 0.880。随着过程逐渐展开，模型可以取得更多标签信息，但最终回答是这个简单文字模型最强的单一局部来源。

#### 明显拒绝与完成词语

研究者根据数据事后建立了一份透明词表，将拒绝、授权、隐私、政策和成功完成等明显短语替换为中性标记。该词表覆盖 942 条记录、1,941 个文字片段；最终回答 Macro-F1 只从 0.880 降到 0.877。

由于这份词表是在看过数据后设计的，它只能算探索性检查。更严格的实验在每个训练折内单独选择权重最大的词，再从训练和测试文本中删除。依次删除 5、10、25、50 和 100 个词语特征后，Macro-F1 为 0.875、0.869、0.859、0.851 和 0.825。结果说明标签信号不是只依赖几个显眼词，而是分散在更多短语中；但删除 100 个特征后已接近完整轨迹基线。

#### 长文本和词汇容量

为了检查完整轨迹是否只是被固定词汇上限不公平限制，项目把 TF-IDF 最大特征数改为 5,000、20,000、50,000 和不设上限。四种设置下，完整轨迹 Macro-F1 分别为 0.849、0.848、0.829 和 0.797；最终回答为 0.884、0.880、0.880 和 0.880。

较小词汇表缩小了差距，却没有消除差距。该结果排除了“只因为 50,000 特征上限”这一狭窄解释，但不能排除 TF-IDF 对长文本的一般性限制。

#### 只看结构而不看文字

一个只使用 23 个数值特征的逻辑回归取得 0.803 Macro-F1 和 0.903 AUROC。这些特征包括事件数量、各角色出现次数、文本长度、工具调用与结果的比例、角色转换、工具多样性和完成位置，但不读取实际文字内容。

这说明 ATBench 的记录结构本身也包含明显标签信号。不过该控制包含是否出现 completion 等信息，因此它是 benchmark 诊断，不能直接作为部署方法。

#### 改变自动分组方法

项目组合了 25、50、75、100 个聚类与 3 个随机种子，共 12 种 group-held-out 设置。完整轨迹 Macro-F1 范围为 0.815 到 0.835，最终回答为 0.870 到 0.880；两者差异范围为 0.035 到 0.061。

结果表明发现不是某一个 K-means 参数独有，但任何近似聚类都不能替代未公开的真实任务家族 ID。

#### 只看真正出现风险来源的案例

ATBench 有 250 条 `risk_source=benign` 的普通安全记录。移除它们，在剩余 750 条风险相关记录上重新聚类和训练后，最终回答达到 0.940 Macro-F1，完整轨迹为 0.831。局部信号并不是只来自“普通安全问题”和“危险问题”的简单区分。

另一方面，在 250 条普通 safe 记录中，最终回答模型错误报警 27.6%，完整轨迹模型错误报警 8.0%。这再次说明最终回答模型不能因为一个综合分数高就被当成严格更好的实际 guard。

### 跨版本迁移

将一个版本上训练的分类器和固定 0.5 阈值直接应用到另一个版本时，表现明显下降，而且两个迁移方向差异很大。例如，ATBench 训练、ATBench500 测试时，最终回答 Macro-F1 为 0.774；反向迁移时只有 0.397，并产生 0.938 的正常误报率。

这类下降可能同时来自任务分布改变和阈值失准。它说明局部信号在单个数据集内部很强，却不一定能形成跨版本稳定的部署规则。

### R-Judge 外部复验

R-Judge 的 group-held-out 结果如下：

| 视图 | Macro-F1 | AUROC | 危险漏报率 FNR |
|---|---:|---:|---:|
| 完整记录 | 0.803 | 0.902 | 0.080 |
| 仅用户信息 | 0.642 | 0.701 | 0.223 |
| 所有 agent 动作 | **0.926** | **0.975** | **0.043** |
| 最后一个 agent 动作 | 0.917 | 0.969 | 0.053 |

最后动作减去完整记录的 Macro-F1 差异为 +0.114；固定 27 个来源文件进行 bootstrap 得到的条件性 95% 区间为 `[+0.052, +0.180]`。这说明强局部动作信号并非只出现在 ATBench，但 R-Judge 的最后动作比 ATBench 的最终回答含义更宽，两个数字不能当作完全相同的实验。

## 预备结果能说明什么和不能说明什么

### 能说明的内容

- 在当前 ATBench 发布数据和透明词汇模型下，最终回答包含很强的 safe 或 unsafe 标签信号。
- 该信号在近似相似任务整组留出、缺失答案检查、词语遮盖、特征容量变化、不同聚类设置和风险相关子集中仍然存在。
- R-Judge 中也存在很强的局部动作信号，因此现象不只出现在一个数据集。
- 只报告完整轨迹模型的一个综合分数，不足以证明模型使用了完整轨迹中的跨步骤信息。

### 不能说明的内容

- 不能说明完整轨迹在现实安全审查中没有价值。
- 不能说明 ATBench 的人工标签错误。
- 不能说明已经发现了训练集答案直接进入测试输入的数据泄漏。
- 不能说明最终回答模型能够发现结果正常但过程越权的 silent fault，也就是“静默过程错误”。
- 不能说明 TF-IDF 结果会原样出现在现代 LLM safety guard 上。
- 不能说明 0.880 的模型可以部署；它仍会误拦正常任务，也没有经过真实分布变化验证。

## 研究问题

本研究以四个问题组织全部实验。

### RQ1 局部信息可以恢复多少标签

只给分类器看用户问题、工具说明、agent 动作或最终回答时，它还能恢复多少 ATBench 的 safe 或 unsafe 标签？

### RQ2 更严格的分组能否消除局部信号

当相似用户请求和工具组合被整组留在测试折、不能同时出现在训练折时，局部视图的表现是否仍然存在？

### RQ3 结果是否可以由简单技术因素解释

观察到的差异是否主要来自缺失最终回答、明显的拒绝或完成词、文本长度、TF-IDF 词汇容量、记录结构或某一个聚类参数？

### RQ4 现代小型安全模型和反事实样本是否重复该结论

换成没有在 ATBench 上训练的冻结小型 guard，并在“动作轨迹不变、最终措辞改变”的人工核验配对样本上测试后，安全判定是否仍然主要受局部结果措辞影响？

RQ1 至 RQ3 已经由预备研究进行探索性回答。RQ4 是 proposed work 的核心，也就是本 proposal 批准后真正需要完成的验证阶段。

## 拟验证的假设

现有结果已经被研究者看过，因此下面的假设只用于约束后续新实验，不能追溯性地把预备分析改写成事先注册的确认性研究。

### H1 小型 guard 仍能从最终回答取得大量标签信息

在固定提示词、固定输出解析规则和不进行 ATBench 微调的情况下，final-answer-only 在小型 guard 上的 Macro-F1 将与 full 处于同一实用量级。暂定的操作标准是：在排除开发小样后的记录上，final-answer-only 的 Macro-F1 不比 full 低超过 0.03。这里的 0.03 是事先选择的“实际差异”界线，不是从预备结果倒推出的显著性门槛；最终仍将报告实际差值及其区间，而不是只报告假设通过或失败。

### H2 单纯改写风格不应大幅改变正确判断

对于含义不变、只是表达风格不同的最终回答，如果安全裁判真正依赖行为证据，它的判断应当大体稳定。过高的配对翻转率表示模型对措辞形式敏感。

### H3 最终回答与实际动作冲突时，完整轨迹应比最终回答更可靠

对于动作已经固定、但最终回答淡化、夸大或错误描述动作的样本，读取完整轨迹的 guard 应比只读最终回答的 guard 更接近依据动作制定的参考标签。

### H4 局部动作信号会在 R-Judge 的小型 guard 复验中继续出现

如果现象不只属于 ATBench 与 TF-IDF，冻结 guard 在 R-Judge 上读取 actions-only 或 last-action-only 时也会表现出较强标签恢复能力。由于 R-Judge 的视图定义不同，该假设只检验方向，不要求复制同一个数值。

## 拟议研究方法

### 工作包一 冻结预备分析

在继续实验前，将现有数据版本、代码、视图定义、折划分、主指标和所有预备结果封存。所有后续变更写入单独的分析计划和运行清单。这样可以避免根据新结果反复调整规则，却仍把最终选择描述为预先决定。

具体工作包括：

- 保存 ATBench、ATBench500 与 R-Judge 的数据哈希或 commit。
- 保存五种主视图及附加视图的确定性生成规则。
- 固定现有 50 组与五折 manifest。
- 将当前结果明确标记为 exploratory preliminary evidence。
- 在运行新 guard 前固定提示词、类别映射、输出解析、最大输入长度和失败处理规则。

### 工作包二 冻结小型安全模型复验

主模型拟采用 [Qwen3Guard-Gen-0.6B](https://huggingface.co/Qwen/Qwen3Guard-Gen-0.6B)，它约有 6 亿个模型参数，并能在 Colab 上以 FP16，也就是 16 位浮点精度运行。资源允许时，再加入 [StepGuard-4B](https://huggingface.co/ninty-seven/StepGuard) 作为第二复验；它约有 40 亿个参数，设计目标更接近逐步骤或整条 agent 轨迹的安全判断。具体模型版本、许可和输入模板将在第 1 周写入冻结配置。第二模型不是最低完成条件。

“冻结”表示项目只做推理，不在 ATBench 上训练或微调模型。这样做有三个目的：

1. 检查局部视图现象是否只来自 TF-IDF 与逻辑回归。
2. 避免在只有一个官方 test split 的数据上进一步训练并过拟合。
3. 将 GPU 需求控制在单张 Colab 显卡可承受的范围。

主实验仍比较 full、user-only、tool-schema-only、actions-only 和 final-answer-only。每条记录在所有视图下使用同一套系统提示、解码参数和输出格式。模型只允许输出 safe 或 unsafe，以及可选的简短分数；自由生成的解释不进入主指标。

输入长度按以下规则处理：

- 首先报告完整轨迹在模型上下文窗口内无需截断的样本比例。
- 对能够完整放入窗口的样本单独报告结果，避免把截断误当成安全推理失败。
- 对超长样本使用事先固定的截断方式，并单独标记。
- 记录每种视图的 token 数、推理时间、显存和解析失败率。
- 不因为某种视图较短，就额外给予更多采样次数或更复杂提示。

0.6B 模型为最低交付；4B 模型如果在第 2 周的 50 条 pilot 中出现显存不足、单位时间能处理的样本数过低，或输出无法稳定转换成 safe 或 unsafe 标签，就从主范围中删除，而不是压缩其他验证工作。

### 工作包三 人工核验的配对反事实

这一部分是从相关性走向更强因果证据的关键。

计划从 ATBench 中分层选取 120 条轨迹，原则上包含 60 条 safe 和 60 条 unsafe，并覆盖不同风险来源与失败模式。每条原始记录生成两类新最终回答，最终形成 120 个三元组：原始版本、含义保持版本和动作报告冲突版本。这样一共有 240 个“原始与改写”配对比较。

1. **含义保持改写。** 保持人物、对象、动作、权限和结果含义不变，只改变句式、礼貌程度、长短和拒绝或完成词的表面表达。
2. **动作与报告冲突的改写。** 保持真实工具动作完全不变，但让最终回答淡化、夸大或错误描述已经发生的动作。例如，轨迹已经执行越权发送，最终回答却声称拒绝执行。此类样本的参考标签由固定的 action-based rubric，也就是以实际动作和授权关系为中心的判定规则决定。

第二类样本不是为了模拟所有现实行为，而是为了建立一个受控测试：当最终文字和实际动作冲突时，安全裁判究竟相信哪一边。

每个改写需要通过以下检查：

- 不改变原始工具调用、参数、工具结果和事件顺序。
- 含义保持组不得改变实际动作是否完成。
- 冲突组必须清楚记录改变了哪一项报告内容。
- 参考标签必须能够由书面 rubric 和具体证据步骤解释。
- 研究者在间隔至少一周后进行第二次盲审，测量自身两次标注的一致性。
- 若能获得第二名审阅者，则额外复核不少于 30 对；该外部复核为加分项，不作为单人 capstone 的完成依赖。

每对样本使用以下配对指标：

- 判定是否翻转。
- 风险分数改变多少。
- 原始与改写版本中，哪一个更接近 action-based reference label。
- full 与 final-answer-only 的翻转率差异。
- 对相同含义改写与动作报告冲突改写分别统计，不能混在一个平均数中。

### 工作包四 R-Judge 的冻结模型外部复验

在 R-Judge 上使用同一个冻结 guard，比较 full、user-only、actions-only 和 last-action-only。模型提示、解析和阈值不得根据 R-Judge 最终结果重新设计。

R-Judge 的最后动作不是正式 final answer，因此结论应写成“局部动作信号的外部复验”，而不是“最终回答结果的完全复制”。主要分组仍按 27 个来源文件进行，并对这些固定来源组做 bootstrap。

### 工作包五 错误分析

定量指标只能说明差异有多大，不能解释模型为什么失败。项目将人工检查约 80–100 个具有代表性的错误，包括：

- Full 正确而 final 错误的案例。
- Final 正确而 full 错误的案例。
- 两个视图都错的案例。
- 反事实改写导致判断翻转的案例。
- Unsafe 漏报与 safe 误报。

错误将被归入预先定义的类型，例如：

- 依赖拒绝或完成措辞。
- 没有追踪数据接收者或授权范围。
- 工具名或参数触发误报。
- 长文本中关键证据被淹没。
- 最终回答忠实总结了过程，因此局部判断合理。
- Benchmark 标签或规则存在合理争议。
- 模型输出解析失败，而不是安全判断失败。

## 评价指标与统计分析

### 主要指标

Macro-F1 为主要综合指标，因为它给 safe 与 unsafe 同样权重。它不会掩盖某一类完全失败的情况，但仍不能表达两种错误在现实中的不同代价。

因此，项目必须同时报告：

- Unsafe FNR，危险漏报率。
- Safe FPR，正常误报率。
- AUROC，排序能力。
- Balanced accuracy，safe 与 unsafe 召回率的平均值。
- 无法解析或没有输出标签的比例。
- 每种视图的 token 数、延迟和峰值显存。

### 配对比较

同一条轨迹的不同视图必须使用相同测试折或同一次冻结模型运行设置。统计比较基于相同记录的配对预测，不能把两组彼此独立的样本当作配对数据。

主要比较包括：

- Final minus full 的 Macro-F1 差异。
- Actions-only minus full 的 Macro-F1 差异。
- Full 与 final 的 unsafe FNR 和 safe FPR 差异。
- 反事实前后的样本级标签翻转率。
- Full 与 final 在反事实对上的正确性差异。

### 不确定性

ATBench 主分析继续对固定的推断组做 group bootstrap。R-Judge 对固定来源文件做 source-group bootstrap。反事实配对使用配对 bootstrap 或精确二项区间。

所有区间都将注明条件范围：它们反映当前固定数据、分组、模型和分析规则下的样本波动，不覆盖研究者选择了哪个模型、哪个提示或哪个 benchmark 的不确定性。

### 多重分析与探索性结果

Proposal 批准后，将指定一个主模型、一个主数据集、一个主视图比较和一个主指标。其他模型、指标、数据切片与错误类别作为次要或探索性分析报告，不会从大量结果中只选择最有利的一项作为主结论。

现有所有 CPU 结果都保持“预备、探索性”标签。新的反事实结果只有在生成规则、样本清单、rubric、模型提示与主要统计方式全部冻结后，才称为验证性结果。

## 可能出现的结果及其解释

| 结果模式 | 合理解释 | 不能得出的结论 |
|---|---|---|
| 简单模型和小型 guard 都在 final 上接近或超过 full | ATBench 标签在最终回答中高度可恢复；benchmark 分数不能单独证明跨步骤理解。 | 不能说完整轨迹没有现实价值。 |
| 简单模型 final 很强，但小型 guard 明显需要 full | 现象可能主要来自 TF-IDF 的表示特点，或现代 guard 能更好利用轨迹结构。 | 不能说预备结果是“错误”；它仍证明简单局部基线的重要性。 |
| 含义保持改写造成大量翻转 | Judge 对表达形式敏感，分数的稳定性有限。 | 不能仅凭翻转认定标签错误。 |
| 动作与最终报告冲突时，final 被误导而 full 正确 | 说明只看结果可能掩盖过程风险，为过程审查提供直接证据。 | 不能保证 full 在所有真实攻击下可靠。 |
| 两种视图在冲突样本上都失败 | 当前 guard 没有可靠追踪动作与授权关系，问题不只是输入长度。 | 不能据此判断所有更大模型都会失败。 |
| R-Judge 不重复 ATBench 的方向 | 局部信号可能依赖 ATBench 的制作方式，外部普适性有限。 | 不能把跨数据集差异自动归因于某一个字段或作者选择。 |

无论哪一种模式出现，项目都有可报告的答案。成功标准是严谨地确定现象在哪些条件下成立，而不是强迫新方法超过已有模型。

## 预期贡献

### 概念贡献

明确区分三个经常被混淆的问题：

1. **标签可预测性：** 模型能否猜中 benchmark 的 safe 或 unsafe 标签？
2. **轨迹理解：** 模型是否真正使用了跨步骤关系？
3. **真实故障检测：** 模型能否在部署环境中发现实际危险？

本项目直接测量第一项，为第二项提供诊断证据，但不会把第一项高分直接当成第三项安全保证。

### 方法贡献

提供一套适用于 agent trajectory benchmark 的低成本审计协议：

- 将同一轨迹确定性拆成完整与局部视图。
- 同时使用随机切分和相似任务整组留出。
- 加入传统透明模型与冻结现代 guard。
- 同时报告漏报、误报、排序和计算成本。
- 使用反事实配对区分相关性与措辞影响。
- 明确记录数据版本、视图规则和分析选择。

### 实证贡献

系统描述 ATBench 和 R-Judge 中哪些局部信息最容易恢复参考标签，以及结果在词语、结构、分组、数据版本和模型类型变化下是否稳定。

### 工程贡献

交付一个可以在 CPU 或 Colab 上复现的开源审计工具。使用者可以为新的 trajectory benchmark 增加数据适配器，并自动生成视图、分组、折外预测、错误指标和报告。

### Benchmark 报告建议

项目最终将形成一份简短 checklist，建议未来轨迹安全数据至少公开或报告：

- 原始任务、场景和配对 family ID。
- 避免相关案例跨 split 的分组规则。
- User-only、action-only、final-only 与结构特征基线。
- Outcome-visible 风险与必须读取过程才能发现的风险分别表现。
- Unsafe FNR 和 safe FPR，而不只报告一个综合分数。
- 输入格式、截断、上下文长度、类别比例和模型阈值。
- 数据版本、许可证与逐样本预测日志。

## 有效性风险与缓解措施

### 风险一 ATBench 没有独立训练集和确认测试集

所有 1,000 条公开记录都已用于探索性分析。五折交叉验证避免了模型直接在同一条训练记录上评分，但不能创造一套研究者从未看过的新数据。

缓解方式是：明确把现有结果称为预备证据；冻结后续分析；使用未运行过的新模型和新构造的配对反事实作为方法层面的复验；不把当前置信区间描述成完整外部重复研究。

### 风险二 近似分组不是真实任务家族

ATBench 没有发布原始 scenario 或 template ID。根据用户文本和工具名生成的聚类可能把真正相关的样本拆开，也可能错误合并无关任务。

缓解方式是同时报告随机折、多个聚类数量和多个随机种子；人工检查部分聚类；若作者未来提供真实 ID，则追加精确 family-held-out 分析。项目不会把 proxy group 写成官方 ground truth group。

### 风险三 简单模型可能不公平地处理长轨迹

完整轨迹平均长度约为最终回答的 53 倍。TF-IDF 的文档归一化、有限词汇表和稀疏表示可能稀释长文本中的少数关键线索。

缓解方式包括特征容量实验、结构特征实验、轨迹前缀实验、长度分层，以及拟议的冻结小型 guard。对于 guard，还会单独报告完整轨迹无需截断的样本。

### 风险四 最终回答可能是合法的结果摘要

如果 safe agent 通常明确拒绝，而 unsafe agent 通常报告工具成功，那么 final-only 得分高可能反映真实结果，而不是错误标注。

本项目的主张因此只限于“局部可预测性”。人工核验的反事实配对将进一步测试模型在动作与最后措辞不一致时相信哪一种证据。

### 风险五 人工反事实可能不自然

研究者改写的文字可能带来新的写作风格，模型也可能据此识别“人工改写样本”。

缓解方式是保留原始长度与语体范围、生成多种改写、记录所有变更、进行延迟盲审，并把含义保持组与动作冲突组分开报告。人工改写的结论不会被外推到所有自然对话。

### 风险六 单个模型不能代表所有 safety guard

0.6B 或 4B 模型的结果不能代表闭源大型模型或其他模型家族。

缓解方式是选择一个低资源主模型和一个可选第二模型，强调这是机制复验而非全面排行榜。项目的主要贡献是审计协议，不是声明某个模型族普遍失败。

### 风险七 数据分布与真实部署不同

ATBench 和 R-Judge 是为研究构造并审核的记录，不是从真实组织的 agent 系统中随机抽取的事故日志。

因此，结果只支持 benchmark validity 结论，不能直接估计现实事故率、攻击成功率或生产系统风险。

## 伦理与安全

本项目分析公开、静态的 agent 记录，不执行轨迹中的工具调用，也不连接真实邮件、网盘、支付、浏览器或企业账户。研究不生成新的可执行攻击链，也不发布绕过安全系统的操作说明。

可能出现的有害文本仅用于分类和错误分析。展示案例时应优先使用抽象或脱敏示例，不复制不必要的敏感细节。研究报告应聚焦 benchmark 设计和 evaluator 可靠性，而不是优化攻击效果。

ATBench 数据按 Apache-2.0 条款使用，该许可证允许在保留必要声明的情况下复用。R-Judge 项目站说明 CC BY-NC-SA，也就是要求署名、仅限非商业使用，并以相同许可证分享改编内容；但固定 GitHub commit 根目录没有明确 LICENSE 文件。因此，本项目只作非商业研究使用，保留来源与版本说明，并避免重新分发许可状态不明确的原始数据。代码与由研究者生成的分析结果可以按仓库既有 MIT 许可发布；第三方数据继续遵守其原许可证。

## 可复现性与数据管理

项目将保留以下材料：

- 数据下载地址、revision、commit 与 SHA-256。
- 数据 schema 检查与标准化日志。
- 每种视图的确定性生成代码。
- 分组、折划分和随机种子 manifest。
- 每条样本的折外预测与模型原始输出。
- 完整指标和 bootstrap 配置。
- 无法解析、截断和缺失输入的逐条记录。
- 反事实原文、改写文本、变更说明和两次人工审核结果。
- 一条命令即可重建主要表格的 README。

下载的数据不提交到代码仓库；代码、配置、数据指纹和不受限制的派生统计可以提交。任何手工修改都必须通过单独的版本化文件完成，不能直接覆盖原始 benchmark。

现有复现入口见 [`capstone/README.md`](README.md)，预备结果见 [`reports/atbench_mvp_results.md`](../reports/atbench_mvp_results.md)。

## 计算资源与可行性

现有 TF-IDF、逻辑回归、聚类和 bootstrap 实验全部可以在 CPU 上运行。保存的运行清单记录，完整的扩展 CPU 实验约用 142 秒完成；这一数字只说明当前传统模型审计很轻量，不代表后续神经网络 guard 也会在相同时间内完成。拟议新增工作不训练模型，只让冻结模型读取输入并输出判断，这一过程称为推理。

最低计算范围为：

- 一个约 0.6B 参数的 safety guard。
- ATBench 1,000 条记录的五个主视图。
- R-Judge 569 条记录的四个视图。
- 约 120 条人工选择轨迹的配对改写。
- 每次处理 1 条或少量记录；这里的 batch 指一次同时送入模型的样本数量。所有输出都会缓存，避免重复推理。

模型提示和解析先在最多 50 条 development pilot，也就是开发小样上固定。这些样本的 ID 会提前写入清单，并从后续 guard 主结果中排除。若完整五视图推理速度不足，则优先保留 full、actions-only 与 final-answer-only 三个核心视图。若 4B 模型超出 Colab 显存或时间预算，则只保留 0.6B 主模型。模型训练、大量设置搜索和大量随机采样均不属于最低交付范围。

项目的主要成本预计是数据审计和人工反事实核验，而不是 GPU 训练。

## 十周执行计划

| 周次 | 主要任务 | 完成判据 |
|---|---|---|
| 第 1 周 | 冻结预备结果、数据版本、研究问题和分析计划；确定主 guard。 | 形成不可随结果修改的配置文件和运行清单。 |
| 第 2 周 | 用最多 50 条记录测试模型加载、上下文长度、提示词、输出解析、显存和吞吐。 | 取得稳定的 safe/unsafe 输出；决定是否保留可选 4B 模型。 |
| 第 3 周 | 在 ATBench 上运行冻结 guard 的 full、actions-only、final-only；资源允许时补 user 与 tool。 | 完成主模型全部原始输出和解析审计。 |
| 第 4 周 | 在 R-Judge 上按固定规则运行同一 guard；完成 group-level 指标。 | 得到外部复验表和版本说明。 |
| 第 5 周 | 分层选择 120 条轨迹，完成含义保持改写和动作报告冲突改写的第一版。 | 每条改写都有机器可检查的 trace identity 与人工变更说明。 |
| 第 6 周 | 完成延迟盲审、必要修订和反事实模型推理。 | 形成最终配对集、审核记录和冻结预测。 |
| 第 7 周 | 运行主要统计、bootstrap、配对翻转分析和长度分层。 | 主表和所有预先指定指标完成。 |
| 第 8 周 | 人工分析 80–100 个错误，完成错误类型与典型案例。 | 每个主要失败类型至少有可解释实例，并保留反例。 |
| 第 9 周 | 整理代码、Colab Notebook、benchmark audit checklist 和演示。 | 从干净环境一条命令重建核心表格。 |
| 第 10 周 | 完成论文、答辩材料和最终复现检查，不再增加新模型。 | 论文区分预备与验证性结果，数字与机器输出一致。 |

## 范围缩减规则

为了保证按时完成，项目预先规定以下缩减顺序：

1. 4B guard 是第一个可以删除的扩展，0.6B guard 保留。
2. 五个 guard 视图如果成本过高，缩减为 full、actions-only 和 final-answer-only。
3. R-Judge 保留核心三视图，不追加第三个 benchmark。
4. 人工来源轨迹可以从 120 条降到 80 条；每条仍保留两类改写，不能删除动作不变的配对设计。
5. 不以减少标签审核、数据隔离或复现记录来换取更多模型。

## 项目完成标准

最低成功标准不是“final 一定比 full 高”，而是完成以下闭环：

- 一个清楚且可证伪的研究问题。
- 固定版本的 ATBench 与 R-Judge 数据。
- 一套通过测试的 full 与 partial-view 生成器。
- 一个透明 CPU 基线和一个冻结小型 guard。
- 相似任务整组留出或明确记录的代理分组。
- 至少 80 条来源轨迹，每条包含含义保持与动作报告冲突两类人工核验改写。
- 同时报告 Macro-F1、AUROC、unsafe FNR 和 safe FPR。
- 对主要差异提供配对不确定性区间。
- 对错误和替代解释进行人工分析。
- 提供能够重建结果的代码、配置和说明。
- 在结论中明确写出研究能说明和不能说明的内容。

如果小型 guard 不重复 TF-IDF 的方向，或者反事实改写几乎不造成翻转，项目仍然完成：这种结果会缩小现象成立的范围，并为 ATBench 的轨迹级有效性提供更强支持。

## 最终交付物

1. 一篇完整 capstone 论文，包含背景、方法、预备结果、验证性结果、限制和伦理讨论。
2. 一个可以在 Colab 或普通 CPU 环境运行的复现仓库。
3. 一个带示例的 Notebook，允许选择一条轨迹并比较不同视图的预测。
4. 一份人工核验的反事实配对数据说明；能否公开原文取决于第三方数据许可。
5. 一份面向 benchmark 作者的 trajectory safety evaluation checklist。
6. 一套答辩图表，重点展示信息视图、错误权衡与结果边界。

## 预期结论的写法

如果后续验证继续支持预备发现，最终结论应谨慎表述为：

> 在 ATBench 及一个外部 agent-safety benchmark 中，局部结果或动作文本包含强参考标签信号。透明文字基线不需要读取完整过程就能取得很高的 benchmark 表现；如果冻结 guard 和动作不变反事实也重复这一模式，那么单一轨迹级分数不足以证明 evaluator 使用了跨步骤证据。未来 benchmark 应同时报告局部视图基线、按任务家族隔离的 split，以及必须依赖过程才能发现的故障子集。

不应写成：

> 完整轨迹没有用，ATBench 已被证明存在泄漏，或者 final-answer-only 模型可以安全部署。
